Companion to Life of a Frame. That guide answers what the code does, in the order a frame does it. This one answers why it exists and how it got that way, in the order the decisions were made. Neither repeats the other: where the mechanism matters, this guide links across rather than re-explaining it; a dashed link with an arrow opens the other guide.

Reader's guide

Quake's source reads like a set of answers with the questions filed off. The expanded collision hulls, the precomputed visibility, the surface cache, the 20 Hz server tick — each is a settled solution to a problem that was live and unsolved in 1995, and several are the survivors of approaches that were built, measured, and thrown away. This guide reconstructs those questions from the public record: Michael Abrash's contemporaneous chapters, the developers' .plan files, and id's own announcements, all archived under docs/historical/.

The material here is evidence-bounded. A claim about what the code does is checkable against the code and is marked with a source reference. A claim about what someone was thinking is only as good as the document it came from, so those are quoted and attributed rather than paraphrased into confident narrative. Where the record is thin, the guide says so instead of filling the gap.

Selected claims carry evidence tags: Code checked against source code; Source reported by a cited document, including paraphrases; Inference reconstructed from the evidence. Tags do not replace citations.

Dates are as published. .plan files were daily worklogs written for a public finger query, not design documents — they are terse, occasionally wrong, and record what was done that day rather than why. Abrash's chapters were written during and shortly after the work, and are the closest thing to a design record that exists.

01 · OriginsBefore Quake: What DOOM Could Not Do

Quake's architecture is easier to read as a list of answers to DOOM's limits than as a design in its own right. DOOM shipped in December 1993 with a renderer built on a two-dimensional binary space partition, sprites for every moving thing, and a fixed camera orientation. Each of those was a deliberate trade that bought a playable frame rate on a 386, and each became a wall that the next engine had to go through rather than around. This chapter establishes what that wall was, using id's own 1993 announcement, Carmack's later retrospective on the DOOM code, and Romero's 1994 announcement of Quake — which described the game before its engine existed.

First pass. DOOM's BSP tree was two-dimensional and was used only for drawing. Quake's is three-dimensional and is used for drawing, collision, and network visibility alike. Almost everything distinctive about Quake's runtime follows from widening that one structure and then finding work for it. Next: the year of prototypes that decided how to use it.

#The 1993 feature list, read as a ceiling

id's DOOM press release of 1 January 1993 is unusually specific about what the engine would do (doom_press_release_1993.txt). It advertises a "fantastic fully texture-mapped environment," non-orthogonal walls, light diminishing and light sourcing, variable-height floors and ceilings, environment animation, palette translation, and four-player networked play. Carmack is quoted with a performance target: "on a 486/33, we're talking 35 frames per second, fully texture-mapped at normal detail, for a large area of the screen."

The list is worth reading twice, because what it omits is the actual subject of this guide. There is no mention of looking up or down, of rooms stacked over rooms, of geometry at an angle to the floor, or of three-dimensional creatures. Those are not oversights in the marketing copy; they are outside what the engine could represent. DOOM's world is a floor plan with heights attached. Walls are vertical, floors and ceilings are horizontal, and no two sectors can occupy the same footprint at different heights.

Two features on that list, however, survive into Quake essentially unchanged, and it is worth naming them now because later chapters depend on them. The first is light diminishing and light sourcing — the observation that lighting is what makes an environment feel like a place, and therefore that lighting is worth spending the frame budget on. Quake's answer is far more ambitious and is covered in surface caching, but the commitment is already visible here. The second is the section headed "An Open Game":

When our last hit, WOLFENSTEIN 3D was released the public responded with an almost immediate deluge of home-brewed utilities; map editors, sound editors, trainers, etc. All without any help on file formats or game layout from Id Software. DOOM will be release as an OPEN GAME. We will provide file formats and technical notes for anyone who wants them. — id Software, DOOM press release, 1 January 1993

That is a 1993 statement of an architectural policy that Quake pushes much further, from published file formats to a shipped bytecode virtual machine with the game logic compiled into a replaceable progs.dat. The QuakeC VM reads as a descendant of this policy. Inference The planned QuakeC chapter will trace that line.

#A binary tree in two dimensions

DOOM's central data structure was a BSP tree, and Carmack's use of it is the reason the technique became widely known. Michael Abrash, writing in 1995 while working alongside him, is explicit about the dimensionality: while searching for Quake's visibility algorithm, Carmack "spent a week on this, as a byproduct devising a perfect DOOM (2-D) visibility architecture, whereby a single, linear walk of a DOOM BSP tree produces zero-overdraw 2-D visibility" (Black Book, ch. 64, "Quake's Visible-Surface Determination"). The parenthesis is doing real work. A DOOM BSP splits the map with lines on a plan view; every splitter is a wall segment, and the tree partitions a floor plan.

That constrains the geometry directly: walls are the map's linedefs, while floors and ceilings are sector properties the renderer fills in between them. Carmack described exactly this structure as the thing he would change, in the notes accompanying the DOOM source release on 23 December 1997 (carmack_doom_retrospective.txt):

The way the rendering proceded from walls to floors to sprites could be collapsed into a single front-to-back walk of the bsp tree to collect information, then draw all the contents of a subsector on the way back up the tree. It requires treating floors and ceilings as polygons, rather than just the gaps between walls, and it requires clipping sprite billboards into subsector fragments, but it would be The Right Thing. — John Carmack, DOOM source release notes, 23 December 1997

Quake removes that constraint at the root of the representation. Its splitting planes carry a full normal vector, not an implied vertical: Code

The key difference is that normal is a vec3_t. Polygons can sit at any angle, so ramps and arbitrary architecture become expressible; leaves are convex volumes rather than convex floor regions, so rooms can stack; and the tree can answer questions about points anywhere in space rather than points on a plan. The cost is a much harder compile. Abrash's chapter 60, "Compiling BSP Trees" builds one in two dimensions, over line segments, to teach the technique; doing it over arbitrary 3-D polygons is qbsp's job, and the splitter heuristic that made it tractable is recorded in chapter 64. The harder consequence is visibility, which the year of discarded renderers covers. The on-disk BSP format and the node and leaf graph it loads into are documented in Life of a Frame.

#The BSP that only drew

The dimensional change is the obvious difference. The more consequential one is what the tree gets used for, and here the best source is Carmack assessing his own code four years later:

The movement and line of sight checking against the lines is one of the bigger misses that I look back on. It is messy code that had some failure cases, and there was a vastly simpler (and faster) solution sitting in front of my face. I used the BSP tree for rendering things, but I didn't realize at the time that it could also be used for environment testing. — John Carmack, DOOM source release notes, 23 December 1997

In DOOM, the BSP tree was built for the renderer. Movement and hitscan traversed the linedefs via the blockmap; line of sight walked the BSP. Quake derives both kinds of query from the same compiled map geometry. Rendering walks the render BSP; collision walks one of the pre-expanded clip hulls, reusing the map's planes. Life of a Frame covers the mechanism in detail: SV_RecursiveHullCheck is the descent, and contents types explain how the engine keeps render nodes and collision hulls separate.

Carmack's retrospective continues straight into the price of doing it that way:

Sweeping volumes for movement gets a bit tougher, and touches on many of the challenges faced in quake / quake2 with edge bevels on polyhedrons. — John Carmack, DOOM source release notes, 23 December 1997

This is the origin of one of Quake's most distinctive and least intuitive structures. Sweeping a player-sized box through a 3-D tree is genuinely hard; reducing that box to a point moving through a tree whose solid volumes have been pre-expanded by the box's dimensions is easy, and reuses the descent unchanged. So qbsp compiles not one tree but several, and each model carries all of them:

with MAX_MAP_HULLS fixed at 4 in WinQuake/bspfile.h:24. The world model uses hulls 0, 1, and 2; slot 3 is unused by the original runtime. SV_HullForEntity picks between them purely on width (WinQuake/world.c:147-153): under 3 units gets the point hull, up to 32 gets hull 1, anything larger gets hull 2. Players and most monsters therefore share hull 1, 32x32x56; hull 2, 64x64x88, is for the large monsters (WinQuake/model.c:959-981).

That is why body sizes come in discrete classes rather than being per-entity: the dimensions are compiled into the map, not chosen at runtime. It is not the reason crouching is absent. Hull 1's vertical extent is standing height, and shrinking an entity's bounding box does not change the hull actually traced against, so a crouch would need its own size class. Slot 3, which the format reserves, was never filled, and the archive does not record why. The three hulls and the way an entity selects or fabricates one are covered in Life of a Frame. The "edge bevels" Carmack mentions are the correction needed to keep expanded polyhedra convex — a detail that only becomes a problem once you have committed to this approach.

The third use of the tree has no direct DOOM counterpart. Because a leaf is a volume, and because visibility between volumes can be computed offline, the same spatial structure that answers "what do I draw" can answer "what does this client need to be told about." Quake's server gates entity updates on the potentially visible set of the leaf each client occupies. That is a networking decision built on a rendering data structure, and the planned shipping-constraints chapter will examine how dialup bandwidth shaped it.

#Announced as a design, not an engine

Quake was public long before it was real. John Romero's .plan of 18 March 1994 announces it by name, with a subtitle, a comparison, and a start date (john_romero/1994-03-18.txt):

.plan. The next game is going to blow DOOM all to hell. DOOM totally sucks in comparison to our next game, QUAKE: The Fight for Justice! QUAKE is going to be a bigger step over DOOM than DOOM was over Wolf3D (ya know -- DOOM = pong). We won't start developing QUAKE until Fall'94, due to Jaguar DOOM (Comlynxed!), commercial DOOM (COMPUSA, Babbage's, etc.) and maybe a DOOM level pack. — John Romero, .plan, 18 March 1994

Two things stand out. The first is the ambition, stated as a ratio rather than a feature: the step from DOOM to Quake was to be at least as large as the step from Wolfenstein to DOOM. Wolfenstein's walls were axis-aligned and eight feet thick; DOOM's could be at any angle and any thickness. The announcement does not say what the next leap would be; the engine that shipped made it a full third dimension. Inference The chapters on discarded renderers and surface caching, followed by the planned one-processor chapter, describe the cost.

The second is the schedule. Quake is announced in March 1994, development is not to begin until autumn, and the game shipped in June 1996. Abrash did not join id until March 1995 (Black Book, ch. 64), by which point "John already had an engine prototyped and a plan in mind" (Abrash, ch. 64) — a plan that the year of discarded renderers examines, and that almost entirely failed to survive contact with the problem. The title The Fight for Justice did not survive either. What shipped shares an ambition with the announcement and little else, a useful calibration of how much of Quake's design was intended in advance and how much was discovered under deadline.

The same .plan records the development environment in passing — "To get the entire world running NEXTSTEP for development" (Romero, .plan, 18 March 1994). NeXTSTEP is why the source has a NeXT build path and why the tools are written the way they are.

One caveat on the evidence in this chapter. The retrospective quoted above was written in December 1997 — after Quake and Quake II. It is reliable testimony about how Carmack understood DOOM's limits in hindsight, and it lines up well with what Quake actually does, but it is not evidence of what he intended in 1994. The contemporaneous record of that period is thin: the March 1994 .plan is the announcement, and there is no public design document between it and Abrash's arrival a year later. Where this guide describes intent before March 1995, it is inference from the shipped code, and says so.

02 · VisibilityThe Year of Discarded Renderers

Between March 1995 and the middle of 1996, Quake's visible-surface determination was rebuilt from scratch repeatedly. A beam tree was written, tuned, and abandoned. At least five other approaches were prototyped or seriously argued and dropped. The design that shipped — precompute, for every leaf in the map, the set of leaves potentially visible from it, then at runtime draw only those — was not on the original plan and arrived within roughly a year of Abrash's joining, well before release. This chapter follows that sequence, because the shape of the surviving code is unintelligible without it: the potentially visible set looks like an obvious idea in hindsight, and reading it as an obvious idea gets its cost model exactly backwards.

First pass. Quake's problem was never "how do I draw a polygon fast." It was overdraw: in a ten-thousand-polygon level most of what is inside the view frustum is hidden behind something else, and drawing it anyway is wasted work that scales with level complexity. The discarded approaches tried to make world visibility tractable at runtime. The one that shipped moved that work offline; runtime rendering still resolved pixel visibility. Next: surface caching and the cost of lighting.

#The problem, stated precisely

Abrash defines the target in chapter 64, "Quake's Visible-Surface Determination", and the definition is worth keeping in mind because every rejected approach failed against one clause of it:

The process of VSD would ideally work as follows: First, you would cull all polygons that are completely outside the view frustum (view pyramid), and would clip away the irrelevant portions of any polygons that are partially outside. Then, you would draw only those pixels of each polygon that are actually visible from the current viewpoint [...] Finally, in a perfect world, the tests to figure out what parts of which polygons are visible would be free, and the processing time would be the same for all possible viewpoints, giving the game a smooth visual flow. — Michael Abrash, Graphics Programming Black Book, ch. 64

Two parts were tractable. A BSP makes coarse frustum culling cheap, because each node bounds a convex subspace, so rejecting one node rejects every polygon beneath it. It also supplies a front-to-back or back-to-front traversal. The hard parts were the middle clause and, above all, the last one.

The last clause does the damage. A painter's-algorithm renderer draws every polygon in the frustum, hidden or not; Abrash estimates worst-case overdraw in a Quake level "10 times or more" (Abrash, ch. 64), meaning each pixel written ten times on average. The problem is not only that this is slow. It is that best case and worst case diverge, so the frame rate swings as the player turns. A design that is fast in a corridor and unplayable in an atrium has not solved the problem.

Abrash, ch. 64. In terms of graphics, Quake is to DOOM as DOOM was to its predecessor, Wolfenstein 3-D. [...] Already, a good-sized Quake level contains on the order of 10,000 polygons, about three times as many polygons as a comparable DOOM level. Local copy

#The prototype, and how long it lasted

Abrash joined id in March 1995, expecting to optimize an existing design:

When I arrived at id at the beginning of March 1995, John already had an engine prototyped and a plan in mind, and I assumed that our work was a simple matter of finishing and optimizing that engine. If I had been aware of id's history, however, I would have known better. — Michael Abrash, Graphics Programming Black Book, ch. 64

The correction is the useful part. By Abrash's count Carmack had by then written "perhaps 20 distinct engines over a four-year period," including "four engines in four weeks" on one occasion. Rewriting the renderer was the normal state of the project, not a crisis in it. Three months after Abrash arrived, "only one element of the original VSD design was anywhere in sight" (Abrash, ch. 64).

This is the single most important piece of context for reading Quake's source. The code is not a first draft that was optimized; it is the last survivor of a long elimination.

#The beam tree

The original design drew front-to-back and tracked, in a second BSP tree, which parts of the screen were still unpainted. That tree was three-dimensional: a beam tree, a set of wedges bounded by planes radiating from the viewpoint.

It starts as one beam — the frustum — with everything outside marked solid and the inside empty. Walking the world tree front-to-back, each polygon is converted into a beam by running planes from its edges through the viewpoint. Whatever part of that beam intersects empty space in the beam tree is visible, and is added to the beam tree as solid. When the beam tree is entirely solid, nothing further can be visible and the walk stops. Drawing happens afterwards: once the tree is complete, the visible portions of the polygons that contributed to it are rasterized.

The reason to use 3-D beams rather than a 2-D screen region is arithmetic. Every beam plane passes through the viewpoint, so testing a vertex against one is a dot product with the plane normal and a sign check, and generating a beam from a polygon edge is a single cross product. There is no projection and no division in the inner test (Michael Abrash, Graphics Programming Black Book, ch. 64). Source

The advantage to working with a 3-D beam tree, rather than a 2-D region, is that determining which side of a beam plane a polygon vertex is on involves only checking the sign of the dot product of the ray to the vertex and the plane normal, because all beam planes run through the origin (the viewpoint). — Michael Abrash, Graphics Programming Black Book, ch. 64, “The Beam Tree”.

It failed on the last clause of the specification. The early-out looks like it caps the worst case, but a view across the top of a level, or out to the sky, never fills the beam tree, so every polygon in the frustum gets tested. Numerical precision left thin cracks that also kept the tree from closing. Abrash's verdict:

in scenes with long view distances, such as views across the top of a level, the total cost of beam processing slowed Quake's frame rate to a crawl. So, in the end, the beam-tree approach proved to suffer from much the same malady as the painter's algorithm: The worst case was much worse than the average case, and it didn't scale well with increasing level complexity. — Michael Abrash, Graphics Programming Black Book, ch. 64

#Five that did not ship

Abrash lists the alternatives that were prototyped "in overnight or weekend-long bursts of coding" (Abrash, ch. 64) or argued and dropped. They are worth recording individually, because each one fails differently and the failures map the design space.

Subdividing raycast. Cast rays on an 8×8 screen grid — cheap, because a ray is just a clip into the BSP tree until it reaches a solid leaf. Where adjacent rays hit different surfaces, cast another between them, recursively, until neighbours agree or are adjacent pixels. This scales with pixel count rather than polygon count, and has no overdraw at all: exactly the right scaling behaviour. It was rejected for correctness, not speed — small polygons can fall between rays and disappear.

Vertex-free surfaces. Store the world as planes only, and extract polygons from plane intersections just before drawing. Clipping becomes fast and the dataset shrinks considerably, since a plane is far more compact than a polygon. Rejected because extracting polygons from planes is expensive at exactly the wrong moment. The shipped on-disk BSP does pool and share planes, but that is ordinary BSP economy rather than a survival of this idea: the vertex-free proposal was that polygons should not be stored at all.

The draw-buffer. An occlusion bitmap with one bit per pixel, recording only whether that pixel has been written. This eliminates overdraw, at the cost of a test in the inner loop, extra writes, cache misses, and, in Abrash's summary, "considerable complexity" (Abrash, ch. 64). The variations considered are a good illustration of how far the search went: test the buffer a byte at a time and skip fully-occluded bytes, or branch from each byte into one of 256 unrolled loops for drawing 0–8 pixels, with the hope of overlapping the perspective divide with pixel processing.

Span-based drawing. Rasterize polygons into spans, clip each new span against a global span list, keep only the nearest at each pixel. Front-to-back walking means little sorting is needed — if there is overlap, the span already in the list is nearer. No overdraw, but every polygon still has to be turned into spans, and the span arithmetic is substantial. This is the closest of the five to what shipped. The edge list and span sorting in the final renderer belong to the same family, though Abrash arrives at edge sorting separately in chapters 66 and 67 rather than by reviving this proposal. The section below returns to it.

Portals. Track the holes in surfaces, since line-of-sight only extends through them. Draw front-to-back; on reaching a portal, clip the polygons and portals behind it to its limits, recursively, until nothing visible remains. This draws only the visible parts of visible polygons — the ideal — but pays for it in a great deal of portal clipping.

The portal approach is the one to keep in view: the shipped PVS preserves its connectivity insight, but precomputes visibility per leaf instead of clipping portals at runtime.

#The breakthrough

Carmack next tried extracting visibility directly from the world BSP tree, reasoning that the beam tree was a second-order structure holding information the world tree already contained implicitly. A week of that produced, as a side effect, a perfect zero-overdraw visibility algorithm for two-dimensional DOOM trees — and, in three dimensions, mounting complexity and persistent glitches. Abrash's account of the weekend that followed is the most-quoted passage in the chapter:

When I came in on Monday, John had the look of a man who had broken through to the other side—and also the look of a man who hadn't had much sleep. [...] At 3:30 Monday morning, as he lay in bed, thinking about portals, he thought of precalculating and storing in each leaf a list of all leaves visible from that leaf, and then at runtime just drawing the visible leaves back-to-front for whatever leaf the viewpoint happens to be in, ignoring all other leaves entirely. — Michael Abrash, Graphics Programming Black Book, ch. 64

The move was to stop computing world visibility at runtime and start looking it up. The discarded approaches tried to make that calculation cheaper; the PVS removes it from the frame loop. Abrash draws the general lesson through a colleague's aphorism — "almost all programming can be viewed as an exercise in caching" (Abrash, ch. 64) — and calls the reframing the inspired part, rather than the algorithm.

The archive does not date this, but it bounds it: Abrash joined in March 1995; chapter 64, written "several months" into his time there with "a few more months to go" (Abrash, ch. 64), describes the PVS prototype as already working and was published while Quake was still unshipped; the game shipped in June 1996. That places the breakthrough in 1995, most likely around the middle of the year and so roughly a year before release. The archive supports no tighter figure than that. Inference

The chapter supplies one correction that this guide should not sand off: Carmack did not experience it as a eureka moment. Abrash reports him saying "precalculating the PVS was a logical evolution of the approaches he had been considering, that there was no moment when he said 'Eureka!'" (Abrash, ch. 64). The dramatic version is Abrash's framing of a colleague's work; the participant's version is that it was a logical next step. Note also what the preceding week was actually spent on: extracting visibility directly from the world BSP tree, not portals. Portals enter at 3:30 on the Monday morning, as the thing he was thinking about when the precomputation idea arrived. Abrash reports both accounts within a few paragraphs of each other, and the gap between them says something about how such designs arrive.

Nor was the underlying idea unprecedented. Abrash's own reference list for the chapter cites Seth Teller's Visibility Preprocessing for Interactive Walkthroughs (SIGGRAPH 91) and his dissertation on visibility in densely occluded polyhedral environments. The archive does not record whether that work was an input; it does establish that precomputed visibility was known in the literature, and that the achievement was making it fit in a 1996 consumer product.

#Making it fit

Abrash reports that the first raw, uncompressed PVS was several megabytes. Four changes brought it down to roughly 20 KB for a good-sized level (Michael Abrash, Graphics Programming Black Book, ch. 64): Source

Size was a concern; initially, a raw, uncompressed potentially visible set (PVS) was several megabytes in size. […] Those steps, along with changing the BSP heuristic to generate fewer leaves (choosing as the next splitter the polygon that splits the fewest other polygons appears to be the best heuristic) and sealing the outside of the levels so the BSPer can remove the outside surfaces, which can never be seen, eventually brought the PVS down to about 20 Kb for a good-size level. — Michael Abrash, Graphics Programming Black Book, ch. 64, “Breakthrough!”.

  1. Store the set as a bit vector, one bit per leaf, rather than a list.
  2. Compress it with run-length encoding of zero bytes, which works extremely well because the rows are sparse. Life of a Frame covers the decompressor.
  3. Change the BSP splitter heuristic to produce fewer leaves. Abrash: "choosing as the next splitter the polygon that splits the fewest other polygons appears to be the best heuristic" (Abrash, ch. 64).
  4. Seal the outside of levels, so the compiler can discard exterior surfaces that can never be seen.

The fourth explains a rule every Quake mapper has met: a leak prevents the normal sealed-world BSP/PVS build from producing valid visibility data. That constraint is not arbitrary strictness — it is what makes the surface count, and therefore the leaf count, and therefore the size of the visibility data, tractable. The format allows up to a megabyte for it (MAX_MAP_VISIBILITY at WinQuake/bspfile.h:44), while the cited good-sized level used about a fiftieth of that.

#What it bought, and what it cost

The PVS is deliberately imprecise. It records what is visible from anywhere in a leaf, not from the actual viewpoint, so it over-reports. Abrash gives the resulting overdraw as "typically on the order of 50 percent but ranging up to 150 percent" (Michael Abrash, Graphics Programming Black Book, ch. 64). Source

the PVS for a leaf includes all leaves visible from anywhere in the leaf, so some overdraw, typically on the order of 50 percent but ranging up to 150 percent, generally occurs — Michael Abrash, Graphics Programming Black Book, ch. 64, “Breakthrough!”.

That inaccuracy is the entire point. Every rejected approach bought precision with runtime work that grew with scene complexity; the PVS accepts bounded imprecision in exchange for a lookup. The payoff is in the third clause of the original specification:

precalculating the PVS results in a leveling of performance; worst case is no longer much worse than best case, because there's no longer extra VSD processing—just more polygons and perhaps some extra overdraw—associated with complex scenes. The first time John showed me his working prototype, I went to the most complex scene I knew of, a place where the frame rate used to grind down into the single digits, and spun around smoothly, with no perceptible slowdown. — Michael Abrash, Graphics Programming Black Book, ch. 64

The cost moved to the map toolchain, where it is paid once by the author rather than sixty times a second by the player. That trade is why vis is slow enough to have its own folklore. The archive does not quantify vis itself, but it does show the stage becoming a prerequisite for the rest of the toolchain: Carmack's .plan of 27 August 1996, describing his new radiosity lighting tool, notes that "you MUST do a vis before running qrad (otherwise it would take about 1000 times longer)." The thousandfold and the tool's 100 MB working set are qrad's, not vis's. The same entry ends with him wanting "to look into" the algorithmic order of full vis processing, "especially now that the vis stage is put before production lighting." Life of a Frame covers how the runtime consumes the result; the GL path keeps a r_novis cvar (WinQuake/gl_rmain.c:86) that switches the whole mechanism off, which is the fastest way to feel what it does.

#The PVS stops being a renderer feature

The clearest evidence that this was a structural decision rather than a rendering optimization is what happened to it afterwards. Carmack's 1996 worklogs show subsystems that have nothing to do with drawing reaching for the PVS. The entries are terse and follow a consistent shape, with * marking completed work and + marking immediate next steps; a plain line is a backlog item. Tracked across six weeks:

.plan. PVS for net update — 15 March 1996, backlog; then * changed network update to client PVS specific — 23 April 1996, done.

That is the moment visibility became a bandwidth policy: the server stopped telling each client about entities the client could not possibly see. The mechanism is SV_FatPVS, and the planned shipping-constraints chapter will examine how dialup shaped it. The same worklogs carry a one-line done-item, "fixed monster sighting PVS problem," on 11 March. That reads like gameplay-visible behaviour depending on compiled visibility data, but a single worklog line will not carry the claim on its own, and the archive says nothing further about it. On 6 April Carmack probes for further uses:

.plan. use PVS to speed line of sight checks? Is that any faster than doing the line check, because it involves two point checks? — Carmack, 6 April 1996

Note that this one is a question, and that it is asked on cost grounds rather than accepted on principle. It is a useful corrective to the tidy version of this story: by 1996 the PVS was infrastructure, but its applicability was still being evaluated case by case.

#What the PVS did not solve

The PVS answers "which leaves might be visible." It does not answer "which pixels are visible," and its deliberate over-reporting actively creates overdraw. Something still has to resolve the remainder.

That is where span-based drawing, rejected on its own above, returns. Abrash describes the shipped renderer at the end of the chapter as the PVS "together with a still-in-development sorted-edge rasterizer that completely eliminates overdraw" (Abrash, ch. 64). The two halves are complementary: the PVS discards most of the world for free, and the edge list resolves what is left exactly. Neither would have been sufficient alone, and the PVS's tolerance for imprecision is affordable precisely because a zero-overdraw rasterizer sits behind it.

Quake still uses a depth buffer for entities, particles and sprites. The world writes depth as it is rasterized, so dynamic geometry can be tested per pixel without making the world depend on a general z-buffer. That is a separate decision, reached in chapter 66, not the rejected draw-buffer coming back: the draw-buffer was a one-bit occlusion mask for the world, and this is per-pixel depth for everything drawn after it. What they share is the recognition that an occlusion structure is affordable once it covers only the geometry that needs one.

The implementation details belong in Life of a Frame. The design decision is the cost split: the PVS discards most of the world cheaply, while the edge list and depth buffer resolve what remains at runtime.

03 · LightingSurface Caching: Making Light Affordable

The visibility work in chapter 2 reduced the world to the pixels worth drawing. Lighting posed a different problem: how to make shadows and highlights stay attached to that world without filling it with extra polygons. Michael Abrash's chapter 68, “Quake's Lighting Model”, traces the change from vertex lighting to lightmaps and cached, already-lit textures. Its argument is about representation before speed: separate the detail of a wall's texture from the detail of its illumination, then reuse their combined result. Chapter 69 tests that choice against hardware with different costs.

First pass. Quake's world lighting stopped depending on polygon vertices. A coarse lightmap and a detailed texture became a lit surface that the renderer could reuse across frames. That bought stable lighting and a simpler drawing loop, at the cost of memory and rebuilding when illumination changed. Next: designing for one processor, where the Pentium shapes the resulting loops.

#The wall that needed too many vertices

Abrash states the world renderer's goal explicitly in chapter 68's “The Lighting Conundrum”: geometry, textures, and lighting should remain fixed under changes of viewpoint. This was a stricter target than the engine applied to moving models, which had their own rendering code and a stronger emphasis on speed. The account concerns walls, floors, and ceilings; it is not a claim that Quake abandoned vertex lighting everywhere.

The initial engine used Gouraud shading. Lighting values lived at vertices and were interpolated across the polygon. That made the geometry carry two responsibilities: describe the wall's shape and supply enough samples to describe its illumination. A large, flat wall needed little geometry, but a spotlight or a shadow across it could need many lighting samples.

Carmack first tried adding a vertex directly beneath a spotlight and splitting the surrounding polygon. Abrash reports that this improved highlights while exposing the cost: more polygons to store, transform, and rasterize, without a corresponding increase in geometric detail. Shadows and overlapping lights demanded further subdivisions. The problem was the coupling, not simply an insufficient polygon budget. Source

A primary problem with Gouraud shading is that it requires the vertices used for world geometry to serve as lighting sample points as well, even though there isn't necessarily a close relationship between lighting and geometry. This artificial coupling often forces the subdivision of a single polygon into several polygons purely for lighting reasons — Michael Abrash, Graphics Programming Black Book, ch. 68, “Problems with Gouraud Shading”.

#Why smaller triangles were not enough

The decisive defect in Abrash's account was visible while turning over a floor. Screen-space interpolation across a Gouraud-shaded quad could change as its screen orientation changed. The lighting appeared to move across the texture. Triangles removed that particular rotational ambiguity, but did not by themselves make the lighting perspective-correct or independent of clipping.

A world built from sufficiently small triangles could hide much of this. It would also increase the database and rasterization work that the visibility effort had been trying to contain. Moving lights made geometry chosen for static illumination an especially poor fit: tomorrow's highlight might need a vertex somewhere else.

Abrash describes weeks of considering alternatives while continuing to use Gouraud shading. His account places the insight at a wall split for a spotlight, with a lighting discontinuity at a T-junction: Carmack wanted to treat it as one surface again. That is the recorded motivation. The chapter does not supply a calendar date for the decision, so this guide does not assign it one.

#Two resolutions, one stable surface

The replacement separated lighting samples from vertices. During map preprocessing, a lightmap stored illumination on a grid spaced every 16 texture texels in each direction. At runtime, the engine combined that grid with the repeated texture tile to build a lit rectangle. The perspective texture mapper then sampled that rectangle without calculating lighting for each screen pixel. Abrash describes this in “Decoupling Lighting from Rasterization”. Source

During off-line preprocessing, a grid, called a light map, is calculated for each polygon in the world, with a lighting value every 16 texels horizontally and vertically. […] Then the polygon is drawn with perspective texture mapping, with the surface serving as the input texture, and with no lighting performed during the texture mapping. — Michael Abrash, Graphics Programming Black Book, ch. 68, “Decoupling Lighting from Rasterization”.

Texture could retain fine detail while illumination varied more slowly. A crack in a stone texture did not require a separate light sample; a shadow did not require another geometric edge. The lightmap was still sampled and filtered, so this was not unlimited lighting resolution. It provided the detail the designers needed without making polygon density determine shadow quality.

Because illumination was attached to the texture before projection, both passed through the same perspective mapping. Turning or clipping the polygon no longer made its light slide relative to its texels. This solved the stability problem at the representation level. The companion guide covers the lightmap data and surface-building mechanism.

#Cache the result, not just the ingredients

A lightmap saves lighting samples; a surface cache saves the work of combining them with texture. These are separate economies. Keeping only the small texture tile and lightmap would still require rebuilding their lit result each time it was needed.

Abrash says Carmack included caching in the design immediately because he expected surface construction to be expensive. If the same surface remained visible, its already-lit pixels could serve another frame. Moving the camera did not inherently change those pixels: perspective mapping selected a new view of them. The expensive work followed changes to the surface rather than every change to the viewpoint. Source

When he thought of surface-based lighting, John immediately realized that surface building would be relatively expensive. […] Consequently, his design included the concept of caching surfaces, so that if the same surface were visible in the next frame, it could be reused without having to be rebuilt. — Michael Abrash, Graphics Programming Black Book, ch. 68, “Surface Caching”.

Separating construction from drawing also made each inner loop easier to optimize. Chapter 68 reports 2.25 cycles per lit texel for surface construction and 7.5 cycles per screen pixel for perspective mapping on a Pentium. These are Abrash's inner-loop figures, not measured whole-frame costs. Texels built and pixels drawn are different quantities; a cache hit can avoid construction, while a partly hidden surface can require building texels that never reach the screen.

The reuse rule is visible in D_CacheSurface: the chosen mip level must have a cached result with the same texture and lightstyle values, and no conflicting dynamic-light state (WinQuake/d_surf.c:264-291). Code The runtime account explains that check and the allocator. The historical point is what it rewards: illumination that stays unchanged across frames.

#Making the cache fit

Combining texture and light destroys the small tile's reuse across differently lit walls. Each cached surface needs its own lit texels. Abrash initially expected several megabytes of surface storage at 320×200, too much for the intended 8 MB machine. His discussion also distinguishes this application cache from the processor's cache: a repeated 64×64 texture tile had good locality; a collection of large, unique surfaces did not.

Two existing decisions made the footprint manageable. The edge-list renderer avoided building surfaces for completely hidden world polygons. Mipmapping reduced the resolution of distant surfaces, with each successive level containing one quarter as many texels. Visibility determined whether construction was necessary; mip selection reduced how much construction and storage it required.

The savings had limits. Seeing part of a surface could still require building its entire rectangle. Choosing one mip level for a very long floor could retain excessive detail in its distant portion. Abrash connects the maximum surface dimensions of 256×256 to this problem. Lighting no longer forced subdivision at every highlight, but storage and sampling still constrained surface size.

Chapter 68 reports that roughly 600 KB sufficed at 320×200 and a little over 1 MB at 640×480. Those are the author's reported budgets, not universal bounds. The worklogs show continued tuning: on 24 May 1996, Carmack listed larger caches for higher resolutions and checking cache-size performance among pending work. On 12 June he recorded completion:

.plan. * increased surface cache size — Carmack, 12 June 1996.

That entry establishes a change, not its size or measured benefit. Neither number should be inferred from the worklog.

#The case reuse could not help

Dynamic lighting exposed the bargain. When illumination changed, the cached combination was obsolete. Abrash's worst case was a frame in which every visible surface needed relighting: construction and texture mapping both had to run, and cross-frame reuse provided no benefit. He called the slowdown tolerable but noticeable, and advised limiting how many surfaces changed at once.

This was therefore more than an implementation detail. A scene with stable architectural lighting suited the cache; widespread, continuous relighting worked against it. That conclusion follows from both the stated limitation and the reuse conditions, rather than from a claim that the archive documents a particular level designer's intent. Inference

Abrash also proposed storing bullet marks, splatters, and other effects in surfaces so their compositing cost could be reused. These are possibilities discussed in chapter 68's closing section, not evidence that original Quake shipped all those effects. The distinction matters: the surface was a place to retain computed appearance, but its potential exceeded the game's implementation.

#What survived the move to hardware

Chapter 69, “Surface Caching and Quake's Triangle Models”, revisits the choice after work on VQuake. Keeping surface caching meant building lit pixels on the CPU and transferring them into accelerator memory. The 16-bit surface format increased construction and transfer costs; larger framebuffers also competed with the cache for memory. A reuse strategy that suited software acquired an additional cost whenever it missed.

Abrash then describes drawing texture and lightmap in separate hardware passes. This retained lighting independent of vertices and consistent under perspective, while avoiding storage of the combined surfaces. Its cost was extra drawing work. The distinction carries into the planned VQuake and GLQuake chapters: lightmaps could survive even when the surface cache did not.

Chapter 3's decision was thus two decisions. Separating illumination from geometry solved a visual problem. Caching the combined surface made that solution economical on the target software renderer. Hardware could change the second answer without undoing the first.

04 · PentiumDesigning for One Processor

The surface cache left Quake with a simpler texture mapper. Making that mapper affordable depended on the machine executing it. The Pentium could issue paired integer instructions and perform integer work while a floating-point divide ran. Quake arranged work to exploit both. Abrash's Graphics Programming Black Book, especially chapter 63, “Floating-Point for Real-Time 3-D”, explains why assumptions inherited from earlier x86 processors no longer held. “One processor” here means a performance target: Quake retained portable C, but its software renderer's costs were shaped around the Pentium.

First pass. Quake did not merely replace C instructions with faster assembly. Its rendering stages provided independent work that the Pentium could execute together: simple integer pixel drawing while the FPU calculated a later perspective correction. Assembly made that arrangement pay; reduced precision shortened the divide itself. Next: shipping constraints, where bandwidth, memory, and deadlines impose further limits.

#Two pipes, one instruction stream

The Pentium's U- and V-pipes could execute two integer instructions together, subject to pairing rules. They were not two processors running separate jobs. Abrash's chapter 20, “Pentium Rules”, describes one instruction stream whose next two instructions could sometimes issue as a pair. The U-pipe handled more operations; the V-pipe handled a restricted subset. Fewer instructions therefore did not automatically mean fewer cycles.

Dependencies mattered as much as instruction choice. If one operation needed the preceding operation's result, putting them beside each other could leave the second pipe idle. Even an otherwise valid pair could stall while an address was being prepared. Chapter 21, “Unleashing the Pentium's V-Pipe”, explains those address-generation interlocks and the lockstep execution that could stall both pipes.

These chapters establish the processor's constraints, not a dated account of Quake's development. Their relevance becomes concrete in chapter 68: separating lighting and tiling from texture mapping made the loops small enough to keep almost all their variables in registers. Source

moving lighting and tiling into a separate loop from texture mapping allows each of the two loops to be optimized very effectively, with almost all variables kept in registers. — Michael Abrash, Graphics Programming Black Book, ch. 68, “Decoupling Lighting from Rasterization”.

The connection to chapter 3 is structural. Surface caching removed lighting calculations from the pixel drawer, leaving fewer live values and simpler repeated operations. This suggests why the separation helped at the instruction level as well as across frames. It does not establish that pairing was the original reason for inventing surface caching; Abrash's account gives the lighting problems that led to it. Inference

#Floating-point stops being the slow alternative

Abrash opens chapter 63 by revisiting his own preference for fixed-point arithmetic. He attributes the change to faster floating-point instructions, a pipelined FPU, and the ability to overlap FXCH, which rearranges the FPU register stack, with other floating-point work. The FPU also supplied eight registers separate from the integer registers. Quake used floating-point inside the span rasterizer, not only for high-level geometry. Source

Quake uses FP all the way down into the inner loop of the span rasterizer, performing several FP operations every 16 pixels. — Michael Abrash, Graphics Programming Black Book, ch. 63, “Not Your Father's Floating-Point”.

The important distinction was between the time an operation took and the useful work possible before its result arrived. Chapter 63 describes pipelined addition, subtraction, and multiplication, but division was different: FDIV occupied the FPU until it finished. Integer instructions could still execute during most of that interval. A following floating-point instruction would stop that progress; the instruction order had to leave enough independent integer work before the next FPU operation.

That made floating-point and fixed-point arithmetic complementary. Floating-point could supply perspective-correct coordinates at intervals, while integer arithmetic advanced through the pixels between them. The assembly walkthrough follows the resulting implementation.

#Give the divide something to overlap

A perspective texture mapper cannot simply advance texture coordinates at a constant rate across an entire receding floor. Quake approximated the curve in short pieces. Abrash's chapter 70, “Quake: A Post-Mortem and a Glimpse into the Future”, describes calculating perspective-correct coordinates every 16 pixels and interpolating between them. He acknowledges slight error, occasionally visible as a small ripple, in return for avoiding the full calculation at every pixel.

Those pixel runs also supplied work to hide division latency. Once the current run's coordinates were ready, the integer side could draw it while the FPU calculated the reciprocal needed for a later correction. Abrash describes the scheduling explicitly. Source

the FDIV to calculate the reciprocal of 1/z is overlapped with drawing 16 pixels, taking advantage of the Pentium's ability to perform floating-point in parallel with integer instructions, so the FDIV effectively takes only one cycle. — Michael Abrash, Graphics Programming Black Book, ch. 70, “Rasterization”.

“Effectively” matters. The divide still took many cycles to finish; useful integer work covered the waiting time. This depended on having work ready that did not need its result. Short runs, setup, and cleanup did not become free. In the sixteen-pixel assembly drawer Abrash is describing, the comment beside FDIV identifies the overlap as the purpose of the preceding setup (WinQuake/d_draw16.s:234-236); the eight-pixel drawer carries the same comment (WinQuake/d_draw.s:230-232). Code

The source also settles which drawer that account describes. On x86, d_subdiv16 defaults to 1 and selects the sixteen-pixel drawer; clearing it selects the eight-pixel one, and the portable build has only the eight-pixel path (WinQuake/d_init.c:27, 148-155). Code Abrash's sixteen-pixel account is the default x86 configuration, not every build or setting.

#Precision was part of the budget

Overlap reduced exposed waiting time. Lower precision reduced the division's actual duration. In chapter 63's “Projection”, Abrash reports 19 cycles for single-precision division; earlier in the chapter he gives 39 at full precision and 33 at double precision. These are Pentium instruction timings, not frame-rate measurements.

The price was changed arithmetic. Abrash warns that reducing FPU precision also affects other operations and can alter clipping results or the tolerances needed for comparisons. Quake's rendering code makes the trade explicit: it calls Sys_LowFPPrecision with a comment saying the purpose is to make FDIV fast, and that leaving this mode active globally would reduce timing precision after extended execution (WinQuake/r_main.c:972-976). It restores high precision before leaving that rendering routine (WinQuake/r_main.c:1047-1048). Code

The mode switch is evidence of a numerical boundary around the rendering work. It is not evidence that less precision was harmless everywhere. The runtime walkthrough traces the control-word changes.

#A target, not a portability ban

Chapter 68 reports 7.5 cycles per mapped pixel for the optimized Pentium loop. That figure describes a loop supplied with spans and a surface to sample. Visibility, surface construction, entities, sound, and game logic still consumed time. Neither pairing nor hiding one divide establishes a twofold improvement in the whole game.

Portable implementations survived alongside the specialized code. Carmack's 23 November 1996 worklog makes the distinction concrete while discussing an ordered NT Alpha machine:

.plan. We aren't going to be able to spend time writing assembly language for it like the intel version has, but it should still run at a pretty decent clip. — Carmack, 23 November 1996.

That records an intended port and a limit on available effort, not measured Alpha performance. It also bounds the chapter's claim: the renderer was portable, while equal tuning across processors was not promised. The Pentium influenced the division of work, the arithmetic precision, and the schedule of the inner loop. Those choices made sense together on the target machine; carrying the C elsewhere did not carry the same costs with it.

05 · ShippingShipping Constraints: Bandwidth, Memory, Deadline

A fast renderer was necessary, but Quake also had to fit a small machine, survive an unreliable connection, and reach a release candidate. Those constraints left different kinds of evidence: Carmack's account of a mistaken networking assumption, worklogs recording memory reductions, and a collision workaround still recognizable in the source. This chapter follows the limits that remained after the rendering decisions. The June worklogs establish what changed near release; later retrospectives explain some of the reasons, without turning every unfinished task into a deadline story.

First pass. Quake spent bandwidth on replaceable world updates, memory on caches it could reclaim, and development time on making the existing system shippable. These choices left costs: modem latency, reduced sound precision on small heaps, and recovery code around collision failures. Next: the planned QuakeC chapter, tracing the separate decision to make game logic replaceable.

#The connection the design expected

Carmack's 2 August 1996 worklog, written after release while developing QuakeWorld, identifies the original assumption directly. He had targeted connections below 200 ms latency; a modem player's path — client, modem, ISP, server, and back — gave him “300+ ms latencies, minimum.” His accompanying figure of 99% of players describes the connections he was discussing, not a measured distribution. Source

My original design was targeted at <200ms connection latencies. […] Unfortunately, 99% of the world gets on with a slip or ppp connection over a modem, often through a crappy overcrowded ISP. This gives 300+ ms latencies, minimum. […] Ok, I made a bad call. I have a T1 to my house, so I just wasn't familliar with PPP life. I'm adressing it now. — John Carmack, 2 August 1996.

Bandwidth and latency were related but distinct. More frequent updates could reduce the time an input waited for server processing. Sending them faster than a modem link could carry them could instead build a queue and delay everything behind it. In the same entry, Carmack describes the existing server loop as collecting input, advancing the world, and sending updates, with a default 20 fps cadence. He explicitly warns that increasing it could overcommit dialup bandwidth and cause severe buffering delays.

That is evidence for a tradeoff, not proof that 20 Hz was an experimentally optimal modem setting. Nor was it a universal limit on every client and listen-server frame. The historical point is that shortening the simulation interval could worsen responsiveness once the connection became the bottleneck. The runtime account of client and server communication supplies the control flow.

#Replace stale state instead of waiting for it

The network design changed before release. In the August entry, Carmack describes QTest's reliable-stream foundation and the later addition of an unreliable sideband. Abrash's chapter 70, “QuakeWorld”, explains the failure that drove the change: waiting for retransmission produced hitches when packets disappeared. Ordinary gameplay state moved to unreliable delivery, with reliable delivery retained for information that could not simply be superseded.

The saving depended on sending only relevant state. As chapter 2 established, the PVS had become a network filter as well as a rendering aid. The surviving encoder also compares entity fields against a fixed baseline, rather than requiring the preceding update packet to decode the next one (WinQuake/sv_main.c:472-512). Code The baseline account explains the format. This gives replaceable updates a useful property: losing one does not break a chain of deltas against successive packets. It does not guarantee that every entity fits in every datagram.

Changing the transport did not remove all delay. Abrash describes keeping the displayed world slightly behind the latest server time so the client could interpolate between received states. Carmack confirms in his 10 August 1996 entry that the shipping version deliberately introduced latency to smooth variable packet arrival. The interpolation mechanism documents what that bought. QuakeWorld's later response belongs in chapter 8; at release, smoothing and responsiveness were still competing goals.

#Memory changed what the player received

Abrash's chapter 68, “Quake's Lighting Model”, identifies an 8 MB machine as the intended target when discussing surface storage. Chapter 3 covers how mipmapping and visibility made that cache fit. The remaining memory pressure reached beyond textures.

On 1 May, Carmack recorded an automatic sound reduction based on available memory:

.plan. * automatic sound decimation based on available memory — Carmack, 1 May 1996.

The surviving sound initialization selects loadas8bit when the engine heap is smaller than 8 MiB (WinQuake/snd_dma.c:196-200). Code That test concerns memory supplied to the engine, not total installed RAM. It establishes a concrete quality trade: sound storage precision could be reduced to fit. The worklog's broader word “decimation” should not be treated as an exact description of this later source revision.

Four days later, the worklog records another memory decision:

.plan. * use all memory between the hunks as dynamic cache — Carmack, 5 May 1996.

This is the resource cache in the memory allocator, distinct from the renderer's cache of lit surfaces. The hunk and cache account describes how cached resources occupy the free space between the hunk's two ends and can be reclaimed when allocations need that space. The policy lets spare memory retain useful assets without reserving that space permanently.

Low-memory behavior was also made testable. On 30 May, the worklog records the option that does it:

.plan. * added -minmemory parm for testing entry case — Carmack, 30 May 1996.

The option survives in Host_Init, where it forces the supplied heap size to the minimum the build requires — one figure for the standard game, another for the level pak (WinQuake/host.c:1035-1046). Code That is stronger evidence than an advertised memory target alone: the program had a way to exercise its constrained configuration on a larger machine.

#The rewrite that did not happen before release

The networking transition changed a fundamental assumption without replacing the architecture built around it. Carmack calls the old code a reliable-stream design retrofitted for unreliable packets. Abrash's retrospective says debugging the resulting system continued until shipping. Source

John did not rewrite the net code to reflect this new fundamental assumption, and wound up with 8,000 lines of messy code that took right up until Quake shipped to debug. — Michael Abrash, Graphics Programming Black Book, ch. 70, “QuakeWorld”.

The line count is Abrash's report, not a count reproduced here. More significantly, neither account establishes that a fixed deadline alone caused the decision against rewriting. They establish an architectural retrofit and a debugging cost that lasted through release. The June worklogs show that tail: 14 June records a fix for stuttering on dropped packets while still listing reliable-message backlog and packet-overflow checks as concerns.

The distinction matters when reading the code. A mechanism can survive because replacing it remains expensive even after its original assumption has changed. Here that interpretation is supported by both developers' later accounts, rather than inferred solely from complicated source.

#A release candidate with recovery code

On 18 June, the worklog records a narrowly described workaround:

.plan. * big hack to catch rare stuck occasions — Carmack, 18 June 1996.

SV_CheckStuck carries a matching description of a hack for rare failures in the world clipping hull (WinQuake/sv_phys.c:754-760). Its recovery attempts use a previous position, then nearby positions, before reporting that the player remains stuck (WinQuake/sv_phys.c:768-799). Code The worklog and comment strongly suggest the same class of workaround, but do not prove that the surviving function is unchanged from that day's implementation. Inference

This is a visible limit of the collision system: recovery was added around a failure that could still occur. The archive entry does not identify its numerical cause or say that a complete collision rewrite was considered. Calling it a workaround is supported; inventing the rejected alternative would not be.

The following day, Carmack recorded creating the “0.9 SW RC distribution” while the same entry still listed bugs and proposed rewrites (19 June 1996). A release candidate is evidence of release preparation, not the final public release date. Together, these entries show what shipping meant in practice: a working system with known limits, recent recovery fixes, and work still deferred. The resulting source preserves those decisions alongside the more deliberate architecture.

06 · QuakeCQuakeC: why a virtual machine

A new map changes where the player goes. New game code changes what happens there: how a monster attacks, what a weapon fires, or which actions earn a point. Quake made that second kind of change possible without rebuilding the engine. Its game rules lived in progs.dat, a compiled QuakeC program that the engine interpreted. The interesting decision was where id drew the boundary: game authors could replace behaviour while the engine kept control of rendering, networking, and the machinery of movement.

First pass. QuakeC made game logic a replaceable program that could travel between engine ports. It kept expensive engine services in C, but charged an interpreter cost for the rules around them. Carmack's later proposal to replace it with native code makes the bargain explicit: speed and debugging on one side, portability and access for mod authors on the other. Next: the planned VQuake chapter, where hardware puts the surface cache through a similar test.

#From editing files to changing rules

The 1993 DOOM announcement promised an “open game.” That promise was specific: id would document formats so players could write tools and share their work. It did not announce a programming language. Source

DOOM will be release as an OPEN GAME. We will provide file formats and technical notes for anyone who wants them. — id Software, DOOM press release, 1 January 1993.

Quake extended that opening into executable behaviour. The connection is a continuity of policy, not proof that QuakeC was already planned in 1993. The sources used here do not record the meeting or prototype in which id first chose a virtual machine. They do show it in use before release, and show game source being distributed afterwards.

On 13 September 1996, Carmack described a beta package containing both the compiled game program and its source. This was an interface id used to ship its own updates, too. Source

It includes quake.exe winded.exe progs.dat, and a zip of the latest .qc files. — Carmack, .plan, 13 September 1996.

The distinction matters. Publishing file formats lets people supply new material to an existing game. Publishing replaceable game code lets them change the rules that give that material meaning.

#Where the engine stops

Consider a projectile hitting a monster. The engine handles movement and detects contact; game code decides what that contact means. Should the projectile explode, bounce, or do nothing? How much damage should it cause? Those decisions can change while the collision machinery stays the same.

The boundary is visible in the callbacks. SV_Impact invokes an entity's QuakeC touch function after contact, while SV_RunThink invokes its think function when nextthink comes due (WinQuake/sv_phys.c:123-174). Code QuakeC supplies the response; the C engine supplies the event. The runtime scheduler shows how those calls fit into a frame.

Map loading uses the same division. ED_LoadFromFile looks up an entity's classname in the program's function table and calls the matching spawn function (WinQuake/pr_edict.c). Code A map can therefore name a new kind of object whose setup lives in game code. The loader does not need a new C branch for every door, pickup, or monster a game author invents.

Calls also cross the boundary in the other direction. QuakeC asks the engine to spawn entities, trace lines, play sounds, and place objects through builtins. These are numbered entry points into C, rather than arbitrary operating-system calls. setorigin, for example, updates an entity's position and relinks it into the world; assigning the position alone would leave the collision links wrong (WinQuake/pr_cmds.c:115-128). Code The builtin interface is where the language reaches the engine's capabilities and its limits.

This gives a mod author considerable room without making every subsystem replaceable. A new damage rule can fit inside QuakeC. A new renderer cannot. Even movement is a shared responsibility: game code can choose velocities and movement modes, but the engine still implements the underlying physics.

#A program that travels with the game

progs.dat contains instructions, functions, strings, variable definitions, and global storage. Its instructions describe operations for Quake's interpreter rather than for a Pentium. A statement has an opcode and three short operands; the instruction set includes arithmetic, branches, function calls, and entity-field access (WinQuake/pr_comp.h:42-125). Code The program format and interpreter are covered in Life of a Frame.

The practical gain is that an engine port can understand the same game program. The mod author does not have to supply a different machine-code binary for each processor and operating system. This is portability of the game logic; maps, models, and other required assets still have to be available, and an engine must support the program's interface.

That interface is deliberately concrete. The loader checks the program version and a checksum for the shared system definitions. The engine and QuakeC agree on fields such as origin, think, and nextthink, while the program can add fields of its own; the loader sizes each entity from the program's field count (WinQuake/pr_edict.c). Code Adding game state need not mean recompiling the engine, but changing the shared layout breaks their agreement.

The VM also carries some of Quake's game conventions directly in its instruction set. OP_STATE sets an animation frame, chooses the next think function, and normally schedules it one tenth of a second later (WinQuake/pr_exec.c:649-661). Code This is a small machine built around this game, with a monster-animation operation beside its arithmetic instructions.

#Still being built near release

The March worklogs show that this machinery was still changing while the game took shape. They record work on the program format, entity storage, and function execution. Source

.plan. crunched progs.dat file structure culled unused edict fields — Carmack, 13 March 1996.

.plan. * made an execution stack for progs — Carmack, 15 March 1996.

These entries establish what was being worked on, not how much memory or time it saved. In the released interpreter, function calls preserve local values on a separate stack before reusing their storage. That makes nested calls and recursion possible; the interpreter walkthrough explains the arrangement. The March entry is consistent with that mechanism, but does not tell us exactly which parts were introduced that day.

QuakeC came with ways to diagnose game code as well. The interpreter counts executed instructions per function and has a runaway-loop guard (WinQuake/pr_exec.c:382-402). Code These help authors locate expensive functions and catch loops that fail to return. They do not turn the VM into a guarantee against hostile programs: the instruction limit does not bound the time spent inside a C builtin, and the engine still has to validate what it loads and executes.

#The bill came due in Quake II

The clearest explanation of QuakeC's costs comes after Quake shipped. On 13 March 1997, Carmack proposed moving Quake II's game logic into a native library. He tied the newly available option to dropping DOS support. Source

I am strongly considering dropping qc in Quake 2 in favor of exporting most of the game logic to a seperate .dll file. This wasn't an option when we had to support dos, but I think it is the correct choice now. — Carmack, .plan, 13 March 1997.

This is later testimony about the constraint, not a surviving design note from Quake's beginnings. In the same entry, he expected native code to improve overall speed by at least 5–10% on full game levels, with less benefit for simple deathmatch modifications. That was a forecast for the proposed change, not a published benchmark. He also wanted a more capable language and a real debugger.

The cost of that move was just as explicit. A native mod would need a separate build for each target platform. Running someone else's machine code raised security concerns, and needing a native compiler would exclude some of the people already writing QuakeC. Carmack acknowledged that the small language had become an entry point into programming. Source

You would actually need a compiler to hack quake. For the serious people, this isn't an issue, but it would cut out a number of people that currently enjoy hacking quake. — Carmack, .plan, 13 March 1997.

QuakeC also needed compilation; the distinction here is the move to a native development toolchain. Faster execution would make some ambitious mods easier to build, while the tools and platform-specific binaries would make others harder to share.

#What survived the language

The decision did not settle permanently in favour of native code. In November 1998, discussing Quake Arena, Carmack returned to interpretation when mod code was moving onto clients. A server operator choosing a native module and a player automatically receiving one from an unfamiliar server presented different risks. Platform-specific client modules would also prevent some engine ports from joining a modded server.

His answer preserved the interpreter while abandoning the custom language. Source

The only real solution to these problems is to use an interpreted language like Quake 1 did. I have reached the conclusion that the benefits of a standard language outweigh the benefits of a custom language for our purposes. — Carmack, .plan, 3 November 1998.

That later choice helps separate two decisions which Quake bundled together: making game logic a portable interpreted program, and inventing QuakeC to express it. The language could be replaced while the reason for the virtual machine remained. Quake had made its rules something an author could compile and distribute separately from the engine. The later games kept renegotiating the cost of that freedom.
