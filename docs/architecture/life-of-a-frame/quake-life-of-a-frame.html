Reader's guide

Quake runs the entire game — input sampling, world simulation, the QuakeC virtual machine, collision, networking, visibility, rasterization and audio mixing — inside one function called once per frame. That function is _Host_Frame in WinQuake/host.c:633, and this document walks it end to end, then drills into each subsystem it touches.

The order of the stages is not incidental — it is the design. A listen server samples the local player's input before simulating the world so the player's own commands are never a frame stale; a pure client sends its intentions after reading the incoming packet so its movement answers the newest server state. The same executable is three different programs depending on two booleans, sv.active and cls.state:

Listen server
Single player or a hosted game. Server and client both run in this process and talk only through the loopback network driver — never through shared memory.
Dedicated server
cls.state == ca_dedicated. Both CL_SendCmd calls no-op, CL_ReadFromServer is skipped, and no framebuffer or sound device is ever opened.
Remote client
sv.active == false. The whole server stage is skipped; the frame is input, network, interpolation, render, sound.

Read it in order for the tour: section 01 establishes the frame skeleton every other section hangs off, 02–04 are the server half (physics and the progs VM, collision hulls and traces, BSP and PVS), 05–07 the client half (both renderers, input and networking, sound and the engine's plumbing). Or click any stage in the diagram below to jump straight to the code that runs there.

Every WinQuake/file.c:NNN reference is a link into the upstream id-Software/Quake tree on GitHub. Line numbers were verified with grep -n against this worktree at commit 3ef8a7a (which has the DOS build restored); upstream is the canonical link target, so a reference may land a line or two off in files the worktree touched.

01 · FrameThe Top-Level Frame: Sys_* Main Loop and Host_Frame

Quake has no engine "framework," no scheduler, no threads, and no event loop in the modern sense. It has a while (1) in a platform file that computes a wall-clock delta and hands it to one function, Host_Frame, which runs everything — input, console, network, the QuakeC world simulation, the client's view of that world, the software or GL rasterizer, and mixing sound — in a fixed, straight-line order, then returns. There is exactly one place where the game advances in time and exactly one ordering of stages, and both the dedicated server and the single-player game are the same code with different flags. This section is the spine that the rest of the document hangs from: it establishes what host_frametime is, why the ordering of stages in _Host_Frame is what it is, and how the client and server manage to be two logically independent programs that happen to share an address space.

#Where it sits in the frame

This is the frame. Everything else in this document is a callee of _Host_Frame (WinQuake/host.c:633-727), which is called from Host_Frame (WinQuake/host.c:729), which is called from a platform main/WinMain loop: WinQuake/sys_win.c:855-888, WinQuake/sys_linux.c:403-429, WinQuake/sys_dos.c:937-950.

#The platform loop: three ports, one shape

The platform layer's entire job at runtime is to answer "how much wall-clock time has passed since the last frame?" and to decide whether it is worth running a frame at all. Every port implements the same shape: sample a monotonic-ish clock, subtract, call Host_Frame(delta), remember the new timestamp.

WinQuake/sys_win.c:852-888:

Two things are worth pulling out. First, the dedicated branch busy-waits on Sys_Sleep() until sys_ticrate seconds (default 0.05, i.e. 20 Hz — WinQuake/host.c:60) have elapsed. A dedicated server has no reason to run faster than its network tick, and burning a Pentium on empty frames would have been actively hostile on the shared machines people ran servers on. Second, the interactive branch never sleeps for a fixed period — it blocks on MsgWaitForMultipleObjects (WinQuake/sys_win.c:673-676), waking on either a timeout or any input event. When the window is not focused it yields; when it is, the loop spins as fast as the machine allows and the rate limiting happens later, inside Host_FilterTime.

The Linux loop (WinQuake/sys_linux.c:402-429) differs in one interesting way — it clamps the accumulator rather than the delta:

oldtime += time is the same as oldtime = newtime here, but the time > sys_ticrate.value*2 branch exists to keep the two from drifting apart after a hitch. On the dedicated path the delta handed to Host_Frame is forced to exactly sys_ticrate.value rather than the true elapsed time — a dedicated server therefore simulates in perfectly uniform 50 ms steps regardless of how badly the host machine hiccuped, which makes server-side physics deterministic and demo/VCR playback reproducible.

The DOS loop (WinQuake/sys_dos.c:937-950) is the most primitive of the three: no sleeping at all, just a continue when a dedicated server hasn't reached its tic. Under DOS there was no OS to yield to, so spinning cost nothing. Sys_FloatTime there (WinQuake/sys_dos.c:689-745) reads the 8253 PIT counter at port 0x40 and the BIOS tick count at real-mode address 0x46c, reconstructing a ~1.193 MHz timebase and defending against the two clocks disagreeing across a latch. It also carries a sametimecount hack that manufactures forward progress if the clock appears frozen for 100,000 consecutive calls — a symptom of just how unreliable the 1996 PC timebase was.

#Host_Frame and the profiling wrapper

Host_Frame (WinQuake/host.c:729-770) is a thin shell. If the serverprofile cvar is zero it simply forwards to _Host_Frame; otherwise it brackets the call with Sys_FloatTime() and prints a rolling average of milliseconds-per-frame and active client count every 1000 frames. All the real work is in _Host_Frame.

The first statement in _Host_Frame is not work but a landing pad:

WinQuake/host.c:640-641. Host_Error (WinQuake/host.c:121) and Host_EndGame (WinQuake/host.c:90) longjmp to this buffer (host_abortserver, declared WinQuake/host.c:52). This is Quake's entire error-recovery strategy: any subsystem, arbitrarily deep — a bad BSP node, a QuakeC runtime error, a dropped server connection — can abandon the frame from wherever it is and the engine resumes at the top of the next one, having torn down the server or disconnected the client on the way out. No unwinding, no cleanup handlers; the hunk allocator is reset to host_hunklevel by Host_ClearMemory (WinQuake/host.c:477) when the level is torn down and that is the whole memory-safety story.

Then rand () is called once per frame, unconditionally (WinQuake/host.c:643-644), with the comment "keep the random time dependent." Advancing the PRNG by wall-clock frame count rather than by simulation events deliberately decouples random outcomes from the deterministic simulation, so two runs at different framerates diverge.

#Host_FilterTime: what host_frametime actually means

Everything downstream reads one global, host_frametime (WinQuake/host.c:40). It is produced here, and it is the single most consequential function in the engine's timing model:

WinQuake/host.c:501-522:

Four separate policies are packed into twenty lines.

Accumulate, don't drop. realtime += time happens on every call, including calls that then return false. The platform loop always advances its own oldtime, so a rejected frame does not lose the elapsed time — it is banked in realtime and shows up in the next accepted frame's host_frametime. This is why the crude oldtime = newtime in the platform loops is correct despite looking lossy.

The 72 Hz cap. 1.0/72.0 ≈ 13.9 ms is a hard ceiling on simulation rate, bypassed only for timedemo. The in-source justification is at the call site, WinQuake/host.c:647-648: // don't run too fast, or packets will flood out. Because a listen server's client sends one clc_move per frame (see CL_SendMove, below) and a server sends one update per client per frame, uncapped frames on a fast machine would multiply outbound packet rate without bound on a 28.8k modem. The cap is a network-bandwidth governor that happens to also bound how often the physics integrator runs.

Slow motion. host_framerate (WinQuake/host.c:57) overrides the measured delta with a constant. Setting host_framerate 0.001 makes the world crawl while the renderer runs flat out — the developer tool that made the "bullet time" screenshots of the era possible, and the mechanism _Host_ServerFrame in the FPS_20 variant leans on.

Clamping. host_frametime is pinned to [0.001, 0.1]. The upper clamp is the important one: a 3-second stall (disk thrash while paging in a level, an alt-tab) must not be handed to SV_Physics as a single 3-second integration step, because Quake's collision code moves entities by velocity * frametime in one shot and would tunnel every moving object straight through the world. Clamping trades time fidelity for the invariant that no entity moves more than ~0.1 s worth of distance per physics step. The lower clamp prevents division blow-ups in friction and acceleration code on absurdly fast frames.

Note that the clamp is not applied when host_framerate is set, and that neither clamp nor cap bounds cumulative drift: after a stall the world is simply behind wall clock and never catches up. Quake makes no attempt at the fixed-timestep-with-accumulator pattern that later engines adopted.

#The order of stages

WinQuake/host.c:650-694 is the canonical ordering. Reproduced with the comments intact, because the comments are the design document:

Sys_SendKeyEvents pumps the platform event queue. On Win32 (WinQuake/sys_win.c:640-655) it drains the message queue with PeekMessage/GetMessage/DispatchMessage; the window procedure turns WM_KEYDOWN etc. into Key_Event calls, and Key_Event for a bound key does not act directly — it Cbuf_AddTexts the binding (+forward, impulse 2, …).

IN_Commands (WinQuake/in_win.c:963, WinQuake/in_dos.c:197, stub at WinQuake/in_null.c:32) lets the joystick driver synthesize button events the same way, since joystick buttons are polled rather than delivered as messages.

Cbuf_Execute (WinQuake/cmd.c:143) then runs the accumulated command buffer. This is why the ordering matters so much: a key pressed this frame has already had its binding executed — setting in_forward.state, firing an impulse — before movement is built. Input latency for a bound key is therefore sub-frame, not one frame, which on a 15 fps 486 was the difference between the game feeling responsive and feeling broken.

NET_Poll (WinQuake/net_main.c:927-953) is not the game packet path. It calls SetNetTime() and runs a time-ordered list of poll procedures — server-list broadcast/collect (WinQuake/net_main.c:308-309), ping tests (WinQuake/net_dgrm.c:570,697), the serial/modem dialing state machine (WinQuake/net_comx.c:1262-1277), IPX housekeeping (WinQuake/net_ipx.c:195). Actual game traffic is read on demand inside SV_RunClients and CL_GetMessage. NET_Poll sits here because it is cheap out-of-band bookkeeping that wants to run once per frame with a fresh timestamp.

CL_SendCmd appears twice, guarded by opposite conditions, and this is the single most deliberate ordering decision in the function. When sv.active — a listen server or single player — the client's intentions must be built before Host_ServerFrame runs, because the server will consume them in the same frame through the loopback socket. When the server is remote, intentions are built after the server stage (which is skipped) and just before CL_ReadFromServer, so the outgoing packet reflects the newest input and goes out as late as possible in the frame — minimizing the input-to-wire latency that dominates on a modem link.

Host_GetConsoleCommands (WinQuake/host.c:532-543) drains Sys_ConsoleInput() for the dedicated-server operator's stdin and injects it into the same command buffer.

Host_ServerFrame runs the world. Its build-time variants are covered below.

host_time += host_frametime (WinQuake/host.c:688) advances the host's own clock, initialized to 1.0 in Host_InitLocal (WinQuake/host.c:235) with the comment "so a think at time 0 won't get called" — a QuakeC entity with nextthink left at its zeroed default must not appear to be due immediately.

CL_ReadFromServer (WinQuake/cl_main.c:634-661) advances cl.time, drains every pending server message, and rebuilds the client's renderable entity list:

Note that the client keeps its own clock (cl.time) driven by the same host_frametime. The client interpolates entity positions between the last two server snapshots (cl.mtime[0], cl.mtime[1]) in CL_RelinkEntities, which is why a 20 Hz server can drive a 72 Hz client smoothly.

SCR_UpdateScreen (WinQuake/screen.c:808 software, WinQuake/gl_screen.c:821 GL) renders. It is called unconditionally, even for a dedicated server — where cls.state == ca_dedicated short-circuits it — and even between the frame's other work, which is why host_speeds brackets it to report the classic tot / server / gfx / snd split (WinQuake/host.c:716-724).

S_Update (WinQuake/snd_dma.c:721) is handed the renderer's view vectors (r_origin, vpn, vright, vup) rather than the client's entity origin, so spatialization matches exactly what was just drawn — including in chase-cam mode. Before signon completes it is called with zero vectors so ambient sounds don't pan wildly during connection. CDAudio_Update (WinQuake/cd_win.c:398, WinQuake/cd_linux.c:328) then services the redbook audio track state machine.

host_framecount++ (WinQuake/host.c:726) is the last statement. It is a frame counter, not a time source; the renderer uses it to mark which BSP nodes and surfaces have already been visited this frame (the standard "visframe" trick), so per-frame visited-flags never need clearing.

#Host_ServerFrame and the FPS_20 road not taken

The shipped server stage is compact (WinQuake/host.c:600-621):

Read: publish the timestep to QuakeC, clear the per-frame unreliable datagram, accept pending connections, ingest client input, simulate, transmit. The pause condition is worth noting — in single player (svs.maxclients == 1) simply opening the console or the menu (key_dest != key_game) freezes the world, without any explicit pause command. In multiplayer that clause is bypassed and only an explicit sv.paused stops simulation.

There is a second, unshipped version guarded by #ifdef FPS_20 (WinQuake/host.c:552-596). FPS_20 is not defined by any makefile in the tree — the only other reference is WinQuake/pr_exec.c:651 — so the #else branch above is what every build compiles. The dead variant is nevertheless instructive: it splits the frame into sub-steps of at most 0.05 s, running _Host_ServerFrame repeatedly while temporarily overwriting host_frametime, then restoring it:

That is WinQuake/host.c:580-591 — a decoupled fixed-ish server tick, the pattern QuakeWorld and every later id engine adopted. It is in the shipped source, disabled, which is a nice fossil of the transition from Quake's fused client/server frame to QuakeWorld's split one.

#Listen server, dedicated server, remote client

The three configurations are not three code paths; they are three settings of two booleans.

Host_FindMaxClients (WinQuake/host.c:157-200) reads the command line once at startup:

  • -dedicated [n] sets cls.state = ca_dedicated and svs.maxclients = n (default 8).
  • -listen [n] leaves cls.state = ca_disconnected but raises svs.maxclients.
  • Neither: svs.maxclients = 1, cls.state = ca_disconnected — single player.

The two are mutually exclusive (Sys_Error at WinQuake/host.c:180), svs.maxclients is clamped to MAX_SCOREBOARD, and deathmatch is auto-set whenever maxclients > 1.

cls.state is a three-value enum (WinQuake/client.h:102-104): ca_dedicated (server only, no client capability at all), ca_disconnected (client running, showing the full-screen console), ca_connected (client talking to some server). sv.active is the orthogonal question of whether this process is running a server.

#How client and server coexist in one process

They do not share state; they share a process and communicate exclusively by messages, exactly as if they were on opposite ends of a modem. The mechanism is the loopback network driver, WinQuake/net_loop.c.

Loop_SendMessage (WinQuake/net_loop.c:154-186) does not send anything — it copies the message into the peer qsocket's receive buffer with a 4-byte header (type byte, 16-bit length, one alignment pad byte), then clears canSend:

Loop_GetMessage (WinQuake/net_loop.c:127-152) pops one message off the front, memmoves the remainder down, and — crucially — re-arms the sender's canSend when it consumes a reliable message. Reliable-message flow control, the same "one in flight at a time" discipline the datagram driver enforces over a real socket, is faithfully reproduced over a memcpy.

The payoff is enormous relative to its cost. Single-player Quake is a network game with a zero-latency link. There is no "local play" code path to keep in sync with the networked one; QuakeC never knows whether the client it is talking to is on the same machine; a bug that only manifests over the wire will usually also manifest in single player if the message sizes get large enough. SV_WriteEntitiesToClient builds and PVS-culls the same delta-compressed entity stream whether the destination is a loopback buffer or a 28.8k modem. Carmack made the same architectural choice in every engine after this one, and the loopback driver is where it starts.

The cost is the coupling this section opened with: because both halves are driven by one host_frametime inside one _Host_Frame, a listen server's simulation rate is the host player's framerate — capped at 72 Hz, but also floored by whatever the host machine manages. A host player with a slow video card slows the world down for everyone connected to them. That defect is precisely what QuakeWorld was built to fix, by moving the server to a fixed tick and letting the client predict.

02 · ServerThe Server Stage: Physics, the QuakeC VM, and Entity Transmission

Host_ServerFrame is where the world exists. In roughly 1600 lines of sv_phys.c, 700 lines of sv_user.c, and a 250-line bytecode interpreter in pr_exec.c, Quake runs a complete rigid-body-ish simulation of every entity in the level, executes game logic written in a custom scripting language, turns each connected client's byte-packed intentions into player movement, and then delta-compresses a visibility-culled snapshot of the world down a 28.8k modem — all in the sub-millisecond budget left over after the software rasterizer has taken its cut. This section follows one server tick from pr_global_struct->frametime = host_frametime to the last NET_SendMessage.

#Where it sits in the frame

_Host_Frame calls Host_ServerFrame (WinQuake/host.c:674-675) once per frame when sv.active, after the client has already deposited its intentions in the loopback socket (CL_SendCmd, WinQuake/host.c:662-663). Host_ServerFrame (WinQuake/host.c:600-621) runs six stages in order: publish frametime to QuakeC, SV_ClearDatagram, SV_CheckForNewClients (WinQuake/sv_main.c:302), SV_RunClients (WinQuake/sv_user.c:600), SV_Physics (WinQuake/sv_phys.c:1507), SV_SendClientMessages (WinQuake/sv_main.c:819).

#SV_Physics: one pass over every edict

The whole simulation is a single linear scan of the edict array, dispatching on one field:

WinQuake/sv_phys.c:1507-1563:

Three structural facts fall out of this loop.

Edict index encodes role. Edict 0 is the world (sv.edicts), edicts 1..svs.maxclients are the player slots — permanently, whether occupied or not — and everything above is a free pool. ED_Alloc (WinQuake/pr_edict.c:87-112) starts its search at svs.maxclients+1 for exactly this reason, and refuses to reuse a slot freed less than 0.5 s ago (WinQuake/pr_edict.c:97) so that in-flight entity references and network entity numbers don't get recycled under a client that hasn't heard about the deletion yet. That comparison also relaxes the rule during the first two seconds of a level, when spawn functions churn through edicts freely.

Player physics is chosen by index, not by movetype. if (i > 0 && i <= svs.maxclients) routes to SV_Physics_Client before movetype is ever consulted; the movetype switch inside that function is a second, narrower dispatch. This is what makes PlayerPreThink/PlayerPostThink player-only hooks without any per-entity flag.

There is no broadphase and no ordering. Entities are simulated in array order, each one moving and colliding against the current state of every other. Simulation results therefore depend on edict index. Quake never pretended otherwise; determinism comes from doing the same thing in the same order every time, not from order-independence.

sv.time += host_frametime at the tail (WinQuake/sv_phys.c:1563) is the world clock. Note it advances after the pass, so every entity in a given frame sees the same sv.time.

The force_retouch global is a QuakeC-settable escape hatch: setting it forces SV_LinkEdict(ent, true) on every entity for a frame, re-running all trigger touches even for things that didn't move. It is decremented once per frame (WinQuake/sv_phys.c:1560-1561), so QuakeC sets it to 2 to guarantee a full retouch pass survives one frame boundary.

#The movetypes

WinQuake/server.h:115-127 defines the taxonomy, and each one is a promise about what physics will do:

  • MOVETYPE_NONE (0) — never moves; only thinks (SV_Physics_None, WinQuake/sv_phys.c:1142-1146). Doors' trigger fields, lights, most static geometry.
  • MOVETYPE_WALK (3) — gravity plus step-climbing; players only.
  • MOVETYPE_STEP (4) — "gravity, special edge handling"; monsters. Falls when unsupported, but does not slide — horizontal movement is driven explicitly by SV_movestep.
  • MOVETYPE_FLY (5) / MOVETYPE_FLYMISSILE (9) — ballistic without gravity; the missile variant uses expanded hulls against monsters.
  • MOVETYPE_TOSS (6) / MOVETYPE_BOUNCE (10) — gravity-driven projectiles; bounce restitution differs.
  • MOVETYPE_PUSH (7) — doors, platforms, trains. "No clip to world, push and crush."
  • MOVETYPE_NOCLIP (8) — integrate position, ignore everything.

SV_Physics collapses TOSS, BOUNCE, FLY and FLYMISSILE onto one handler, SV_Physics_Toss (WinQuake/sv_phys.c:1245), which branches internally on gravity.

#SV_RunThink: the QuakeC scheduler

Almost all game behavior in Quake is a chain of deferred think calls, and the entire scheduler is fourteen lines:

WinQuake/sv_phys.c:126-144:

There is no priority queue, no timer wheel: every entity is polled every frame and the nextthink <= sv.time + host_frametime test is the whole scheduling policy. On a 200-edict level at 20 Hz that is 4,000 float comparisons per second — genuinely cheaper than maintaining a heap, and utterly predictable. Two details matter downstream. The QuakeC-visible time global is set to the scheduled think time, not the actual sv.time, so a think that reschedules itself with self.nextthink = time + 0.1 accumulates no drift. And the return value is !ent->free — a think function that calls remove(self) makes every caller bail out immediately, which is why SV_Physics_Client and SV_Physics_Toss are littered with if (!SV_RunThink (ent)) return;.

The function header's own comment (WinQuake/sv_phys.c:120-122) admits the imprecision: "There is some play in the exact time the think function will be called, because it is called before any movement is done in a frame. Not used for pushmove objects, because they must be exact." Pushers get the exact treatment in SV_Physics_Pusher (below), because a door that overshoots its think time by a frame ends up geometrically in the wrong place, whereas a rocket that thinks 8 ms late just moves 8 ms further.

#SV_FlyMove: the sliding-collision core

Every non-trivial mover funnels into SV_FlyMove (WinQuake/sv_phys.c:229-362) — players, monsters in freefall, projectiles. It is an iterative trace-and-slide, capped at four bounces:

The 0.7 threshold on plane.normal[2] — roughly 45.6° — is Quake's definition of "floor," and it appears verbatim in half a dozen places (WinQuake/sv_phys.c:281, WinQuake/sv_phys.c:1033, WinQuake/sv_move.c). Steeper than that and it's a wall you slide down; shallower and you stand on it. There is no separate slope-friction model.

#Gravity, velocity bounds, and NaN defense

SV_AddGravity (WinQuake/sv_phys.c:371-390) is one line of physics wrapped in a per-entity gravity scale looked up by name through GetEdictFieldValue(ent, "gravity") — a reflective field lookup into the progs field table, so a mod can add a .gravity field without any engine change:

sv_gravity defaults to 800 (WinQuake/sv_phys.c:44) — 800 Quake units/s², with a unit conventionally read as about an inch, so ~20 m/s², about twice Earth gravity. Quake's world is deliberately heavier and snappier than reality.

SV_CheckVelocity (WinQuake/sv_phys.c:90-114) clamps each axis to sv_maxvelocity (2000, WinQuake/sv_phys.c:45) and — notably — explicitly tests for NaN in both velocity and origin, printing the offending entity's classname and zeroing the component. That check is defensive engineering born of experience: a single NaN propagating into SV_Move would poison the BSP hull traversal and crash the server, so the engine scrubs it every frame rather than trying to find the source.

Note that the clamp is per axis, not on the magnitude — a diagonal move can exceed 2000 units/s by √3. This is the same class of shortcut that made diagonal running faster than straight running in the original games.

#Water

Water is handled as a content type sampled at up to three points on the entity's bounding box. SV_CheckWater (WinQuake/sv_phys.c:808-...) probes at mins[2]+1, at the box midpoint, and at the view height, setting waterlevel to 0–3 and watertype to the BSP content value:

Pushers get their own timebase. Every MOVETYPE_PUSH entity carries ltime, a private clock that is not sv.time, and SV_Physics_Pusher (WinQuake/sv_phys.c:704-743) shortens the frame's movement so the pusher lands exactly on its think time:

The cost is that ltime can lag sv.time when a pusher is blocked, and SV_PushMove (WinQuake/sv_phys.c:439-557) explicitly rewinds it (pusher->v.ltime -= movetime, WinQuake/sv_phys.c:535) when it cannot complete.

SV_PushMove itself is the crush handler. The corpse special case at WinQuake/sv_phys.c:521-528 — collapsing a blocking non-solid entity's bounding box to a point rather than failing the move — is pure pragmatism: a dead body should never stop a door.

#SV_Physics_Client and player movement

Players are the only entities that get QuakeC hooks on both sides of their move:

Crucially, the velocity the move uses was already computed, earlier in the frame, by SV_ClientThink inside SV_RunClients. The split is: SV_RunClients turns network input into velocity; SV_Physics_Client turns velocity into position.

#The QuakeC VM

Quake's game logic is not C. It is compiled QuakeC, shipped as progs.dat, loaded by PR_LoadProgs (WinQuake/pr_edict.c:985) and interpreted by PR_ExecuteProgram (WinQuake/pr_exec.c:361). This is the design decision that made Quake moddable and is directly responsible for Team Fortress, Threewave CTF, and the entire mod culture that followed.

#The image

progs.dat is six lumps plus a header (WinQuake/pr_edict.c:1010-1021):

The file is loaded onto the hunk and used in place — no relocation, no linking, just pointer arithmetic into the mapped image and a byte-swap pass for big-endian hosts. pr_globals and pr_global_struct are the same memory viewed two ways: the engine reads named fields through the C struct globalvars_t (WinQuake/progdefs.q1:4-60) while the interpreter indexes the same words as a flat float[]. That aliasing is validated by a CRC check against PROGHEADER_CRC (5927, WinQuake/progdefs.q1:143) at load time (WinQuake/pr_edict.c:1009-1010) — if a mod author changes the system globals or fields, the engine refuses to run rather than silently reading garbage.

pr_edict_size is the key line: an edict is a C edict_t header (WinQuake/progs.h:35-49) whose last member is an entvars_t, followed immediately by however many extra 4-byte fields the mod's progs declared. NEXT_EDICT, EDICT_TO_PROG, and PROG_TO_EDICT (WinQuake/progs.h:94-97) are byte-offset macros over that variable stride, and QuakeC's entity type is literally a byte offset from sv.edicts. Extra fields are reached reflectively via GetEdictFieldValue and the fielddef table — which is exactly how SV_AddGravity finds a mod-defined .gravity.

#The interpreter

PR_ExecuteProgram (WinQuake/pr_exec.c:361-666) is a straightforward switch-dispatch loop over a fixed-format three-address instruction:

WinQuake/pr_exec.c:390-412:

Every operand is a 16-bit index into one flat pr_globals array — there are no registers and no stack machine. The compiler allocates temporaries as globals, which makes the interpreter trivially fast (three array indexes and a switch per instruction) at the cost of making QuakeC non-reentrant in an interesting way: recursion works only because PR_EnterFunction (WinQuake/pr_exec.c:294-326) copies the callee's local slots onto a shadow stack before overwriting them:

PR_LeaveFunction (WinQuake/pr_exec.c:333-353) copies them back. Locals are statically allocated globals with save/restore around calls — a callee-saves convention implemented in software.

The runaway = 100000 counter (WinQuake/pr_exec.c:382, decremented at :399) is the sandbox: a buggy mod cannot hang the server, it gets a PR_RunError with a QuakeC stack trace (PR_StackTrace, WinQuake/pr_exec.c:190) that longjmps out through Host_Error to the top of _Host_Frame. pr_xfunction->profile++ on every instruction is a free per-function instruction counter, dumped by the profile console command (PR_Profile_f, WinQuake/pr_exec.c:222) — the mod author's optimization tool, built into the shipping engine.

Two opcodes are not general computation at all. OP_CALL0–OP_CALL8 (WinQuake/pr_exec.c:620-636) reuse a negative first_statement as a builtin index:

#Builtins

The engine↔progs boundary is a flat function-pointer table, pr_builtin[] (WinQuake/pr_cmds.c:1831-1931), indexed by the negative first_statement above, with pr_numbuiltins computed by sizeof (WinQuake/pr_cmds.c:1933). There are about 80 of them and they are the only way progs can touch the world: setorigin (WinQuake/pr_cmds.c:120) because assigning .origin directly would skip SV_LinkEdict, setmodel (WinQuake/pr_cmds.c:234) because model indices must be interned in the precache table, traceline (WinQuake/pr_cmds.c:609) for hitscan, spawn/remove for edict lifetime, sound/bprint/stuffcmd for output.

The commented-out builtin numbers in the table (// float(vector v1, vector v2, float tryents) traceline = #16;) are the actual interface contract — QuakeC declares traceline = #16 and the compiler emits a function whose first_statement is -16. Adding a builtin means appending to this array; the number is its position, forever.

#PVS gating

The visibility cut is the single biggest bandwidth lever, and it reuses the BSP's precomputed potentially-visible set.

SV_FatPVS (WinQuake/sv_main.c:410-416) does not take the PVS of the leaf containing the eye. It ORs together the PVS of every leaf within 8 units of the eye point:

SV_AddToFatPVS (WinQuake/sv_main.c:367-400) walks the BSP from the root and, whenever the eye is within 8 units of a splitting plane (if (d > 8) ... else if (d < -8) ... else descend both children), takes both sides. The header comment (WinQuake/sv_main.c:356-359) explains why: without it, "an entity that should be visible [does] not show up, especially when the bob crosses a waterline" — view bob moves the eye a few units per frame, and a hard leaf lookup makes entities pop as the eye crosses a plane. Widening the query by 8 units in every direction costs a handful of extra leaf ORs and eliminates the flicker. Note the recursion is only on the near-plane case; the common path is an iterative descent.

SV_WriteEntitiesToClient (WinQuake/sv_main.c:427-...) then scans all edicts and drops anything not touching that set:

The per-entity leaf list (ent->leafnums[], up to MAX_ENT_LEAFS = 16, WinQuake/progs.h:34, WinQuake/progs.h:40-41) is maintained by SV_LinkEdict in world.c — the same call that keeps the areanode tree current for collision also records which BSP leaves the entity's bounding box straddles. So the visibility test is a 16-iteration bit test against a bitfield, per entity, per client. No frustum, no distance, no occlusion queries: a static precomputed cell-to-cell visibility matrix does all the work, at the cost of a lengthy vis compile step and the classic Quake artifact of entities in an adjacent-but-visible room being culled when they shouldn't be.

Two consequences worth naming. First, this is also an anti-cheat measure by accident: a wallhack cannot show you a player the server never told you about. Second, an entity with no model (!ent->v.modelindex) is never transmitted, which is why QuakeC's invisible logic entities — triggers, spawn points, path corners — cost zero bandwidth despite existing in the edict array.

#Delta against baseline

Each surviving entity is compared not against the previous frame but against a per-entity baseline captured at level load by SV_CreateBaseline (WinQuake/sv_main.c:925) and sent once during signon. SV_WriteEntitiesToClient builds a bitmask of what differs (WinQuake/sv_main.c:472-512) and writes only those fields:

Baseline-relative rather than previous-frame-relative delta is a deliberate simplification: the server keeps no per-client history, so it never has to track which frames a client actually received, and a dropped packet self-heals on the next one. The price is that a moving entity re-transmits its position every frame forever, which is why QuakeWorld switched to true per-client delta with acknowledged frames. The U_MOREBITS / U_LONGENTITY escape hatches (WinQuake/sv_main.c:508-512) keep the common case at one byte of bitmask and one byte of entity number — most updates are 4–8 bytes total.

U_NOLERP for MOVETYPE_STEP is the client-interpolation opt-out. Monsters animate at 10 Hz via OP_STATE and teleport between poses; interpolating their origins would smear the deliberate snap of the animation.

03 · CollisionCollision: Hulls, Traces, and Hit Detection

Quake does not do collision detection against triangles. It does not do collision detection against the polygons you can see at all. Instead, the map compiler precomputes three separate BSP trees per map — one for a point, one for a 32×32×56 box, one for a 64×64×88 box — in which the world geometry has been dilated by the size of the moving object, so that at runtime every collision query degenerates into a line trace through a point in a solid/empty BSP. Bounding boxes of non-world entities are turned into six-plane BSPs on the fly so they can go through the exact same code. The result is that SV_Move, the one collision entry point the whole engine uses, resolves a swept-box-vs-world query in a few dozen float compares and a handful of recursive descents — no triangle tests, no GJK, no broadphase sweep, nothing that would have been affordable on a 75 MHz Pentium. This section covers that machinery, the areanode structure that culls entity-vs-entity tests, and how it all surfaces to game code as traceline.

#Where it sits in the frame

Collision has no stage of its own. It is a service called from inside the server stage (Host_ServerFrame → SV_Physics, WinQuake/host.c:617), and almost every interesting call chain in the previous section bottoms out here: SV_FlyMove (WinQuake/sv_phys.c:260), SV_PushEntity (WinQuake/sv_phys.c:408), SV_UserFriction's edge probe (WinQuake/sv_user.c:142), SV_CheckWater via SV_PointContents (WinQuake/sv_phys.c:822), SV_movestep for monsters (WinQuake/sv_move.c:138,163,171), and the traceline builtin from QuakeC (WinQuake/pr_cmds.c:621). The client also calls the hull code directly for the chase camera (WinQuake/chase.c:55).

#trace_t: the universal result

Every query returns the same eight-field struct (WinQuake/world.h:28-37):

The distinction between allsolid and startsolid is load-bearing and easy to get backwards. startsolid means the trace began inside a solid — the mover is embedded — but it may still have found open space along the way. allsolid means it never left solid at all. The header comment on SV_Move (WinQuake/world.h:72-75) states the resulting policy explicitly: "if the starting point is in a solid, it will be allowed to move out to an open area." That is a deliberate, forgiving choice — a player who ends up stuck (through a telefrag, a moving platform, or float error at a hull seam) can escape rather than being frozen forever. SV_FlyMove turns allsolid into "kill velocity, return 3" (WinQuake/sv_phys.c:262-266), but tolerates startsolid silently.

inopen / inwater record the content types the trace passed through; SV_ReadClientMessage-driven QuakeC uses them via trace_inopen / trace_inwater to distinguish a shot that crossed a water surface. fraction is parametric along the move, so callers scale their own velocity by it rather than recomputing distances.

#The three hulls

This is the central idea, and it is worth being precise about what "hull" means. A hull_t (WinQuake/model.h:169-177) is a self-contained BSP:

Why three? Because dilating the world by the mover's size at compile time turns a swept-box test into a swept-point test at runtime. This is a Minkowski sum baked into the data. If you push every wall inward by 16 units on X and Y, 24 down and 32 up, then a player box colliding with the real world is exactly a player point colliding with the dilated world. qbsp does this expansion once, offline, so the runtime never has to consider the mover's extents at all — SV_RecursiveHullCheck only ever traces a line.

The cost is the defining constraint of Quake level design and gameplay: there are only three collision sizes in the entire game. Every entity is snapped to the nearest one by SV_HullForEntity. A grenade, a nail, a health box, and an ogre's fireball all collide as points against the world (hull 0). Every player and most monsters collide as a 32×32×56 box (hull 1). Shamblers and other large monsters use 64×64×88 (hull 2). Nothing in between exists. This is why Quake's monsters come in exactly two footprints, why doorways are sized the way they are, and why a rocket passes cleanly through a gap that the player who fired it cannot fit through.

Fabien Sanglard's review and Olivier Montanuy's Unofficial Quake Specs both cover the hull expansion from the BSP-format side; the specs document the clipnode lump and the per-model headnode[] array that selects which hull a submodel uses.

#SV_HullForEntity: picking or fabricating a hull

Everything funnels through this selector (WinQuake/world.c:129-171):

Two paths. For SOLID_BSP — the world itself, and every door, platform, and train, which are BSP submodels — hull selection is a two-branch decision on the X size alone of the moving object. Not the largest dimension, not a volume: size[0]. That is fine because the three hulls only ever differ meaningfully in their horizontal footprint and the mover sizes are drawn from a tiny fixed set, but it is exactly the kind of shortcut that makes this code fast and inflexible in equal measure.

The offset output is the coordinate correction. Because the dilated hull was built assuming the mover's origin sits at a specific position within its box, the caller's world-space start/end must be shifted into the hull's frame — VectorSubtract (hull->clip_mins, mins, offset) computes exactly the discrepancy between the hull's assumed box and the actual box, then adds the entity's origin so a moving door's hull travels with it.

The else branch is the elegant part. A non-BSP entity — a monster, an item, another player — is not special-cased. Its axis-aligned box is expanded by the mover's box (ent->v.mins - maxs … ent->v.maxs - mins: again a Minkowski sum, this time computed at runtime) and handed to SV_HullForBox, which patches six plane distances into a permanently-allocated 6-node BSP:

The topology was built once at level load by SV_InitBoxHull (WinQuake/world.c:68-94), which chains six clipnodes so that "inside all six planes" reaches CONTENTS_SOLID and falling outside any one reaches CONTENTS_EMPTY. #SV_Move and the areanode tree

SV_Move (WinQuake/world.c:923-961) is the public entry point, and it is short because all it does is compose: trace the world, then trace whatever entities the move's bounding box could reach.

MOVE_MISSILE (WinQuake/world.h:42) is a gameplay cheat with a clean implementation: a rocket is a point against the world but a 30-unit cube against monsters, via the separate mins2/maxs2 used only in the monster branch of SV_ClipToLinks (WinQuake/world.c:857-860). #SV_TouchLinks

Trigger dispatch (WinQuake/world.c:277-319) walks the trigger lists of every areanode the entity's box overlaps and calls QuakeC:

Three details. next = l->next is captured before the QuakeC call, because a touch function can legally remove() the trigger and unlink it mid-iteration — the classic teleporter/pickup case. The self/other globals are saved and restored around the call because SV_TouchLinks can be re-entered: a touch function that calls setorigin re-enters SV_LinkEdict and hence SV_TouchLinks. And the touch is a pure AABB overlap test — triggers are boxes, never hulls, so a trigger's shape is exactly its bounding box regardless of the brushes it was built from.

Trigger detection is thus decoupled from movement: SV_FlyMove handles blocking collisions and calls SV_Impact, while triggers fire from the post-move relink. That is why walking through a trigger never slows you down and why a very fast projectile can pass through a thin trigger between frames without firing it — the check is on the endpoint, not the swept volume.

Projectiles are edicts. So: hitscan is N traces resolved this instant with no entity created; projectiles are one entity traced once per frame until something touches it. The tradeoff is exactly the one you would expect — hitscan costs CPU at fire time and nothing thereafter, projectiles cost an edict slot, per-frame physics, and network bandwidth for as long as they fly. On a 1996 server with MAX_EDICTS at 600, that mattered.

04 · WorldBSP and PVS

Every Quake level is a single binary-space-partitioned tree baked at compile time by qbsp/vis/light, then loaded verbatim into a handful of flat arrays. The BSP tree gives the engine two things it cannot afford to compute per frame on 1996 hardware: a way to walk the world strictly front-to-back (or back-to-front) without sorting, and a precomputed potentially-visible-set (PVS) that turns "which leaf is visible from here" from an O(leafs) visibility test into a byte-array lookup. This section covers the on-disk format, the loader in model.c that turns it into the in-memory mnode_t/mleaf_t/hull_t graph, how the renderer marks visible leaves from the PVS, how the server reuses the exact same PVS machinery to decide what to network to each client, and the two lighting subsystems (r_light.c) that ride on top of the same BSP walk: static lightmap sampling and dynamic light surface-marking.

#Where it sits in the frame

On the client, SCR_UpdateScreen (WinQuake/screen.c:808) calls V_RenderView (WinQuake/screen.c:893 invocation, defined WinQuake/view.c:995). V_RenderView calls R_PushDlights (WinQuake/view.c:1018, defined WinQuake/r_light.c:115) to re-mark which surfaces are touched by dynamic lights this frame, then calls R_RenderView. In the GL renderer that leads into R_RenderScene (WinQuake/gl_rmain.c:949), which calls R_MarkLeaves (WinQuake/gl_rmain.c:957) — the PVS walk that flags which BSP nodes are potentially visible from the player's current leaf — immediately before R_DrawWorld walks the tree and emits surfaces. The software renderer's equivalent path is R_RenderView_ (WinQuake/r_main.c:953) calling R_MarkLeaves at WinQuake/r_main.c:967.

On the server side, PVS is consulted once per client per frame inside SV_WriteEntitiesToClient (WinQuake/sv_main.c:427), called from the server's per-client network update pass during SV_SendClientMessages / Host_ServerFrame. This is a separate PVS computation (SV_FatPVS) from the client's rendering PVS (Mod_LeafPVS/R_MarkLeaves) even though both ultimately call the same Mod_DecompressVis.

#On-disk BSP format

The whole map file is one blob: a dheader_t (WinQuake/bspfile.h:82-95) holding a version number and 15 lump_t {fileofs, filelen} directory entries (WinQuake/bspfile.h:59-80), version-locked to BSPVERSION 29 (WinQuake/bspfile.h:56). There is no per-lump alignment or compression beyond the visibility lump's own RLE scheme — everything is packed contiguously and referenced by byte offset, which is what lets the loader mmap/read the whole file once and then just point structures at offsets into it (see mod_base usage below).

The key on-disk structures:

  • dplane_t (WinQuake/bspfile.h:128-133): a normal + distance + type (whether the plane is axis-aligned, used to fast-path dot products).
  • dnode_t (WinQuake/bspfile.h:155-163): a render-tree node — planenum, two children[] (a non-negative index is another node, negative is -(leaf+1)), a 16-bit bounding box for frustum culling, and firstface/numfaces into the face list. Note children are short — capped at MAX_MAP_NODES 32767 (WinQuake/bspfile.h:32) specifically because negative shorts double as leaf indices.
  • dclipnode_t (WinQuake/bspfile.h:165-169): the collision tree node — just planenum and two children[], where negative values are literal CONTENTS_* constants, not leaf indices. This is a much thinner structure than dnode_t because clipping only needs to answer "solid or not," not "which surfaces are here."
  • dleaf_t (WinQuake/bspfile.h:213-225): contents (a CONTENTS_* enum, always negative — WinQuake/bspfile.h:137-151), visofs (byte offset into the decompressed-on-load visibility lump, or -1), a 16-bit bbox, a marksurface range, and four ambient_level bytes used for distance-attenuated ambient sound (water/sky/slime/lava hum).
  • dface_t (WinQuake/bspfile.h:188-200): planenum/side, an edge range (firstedge/numedges into the surfedges indirection list), texinfo, up to MAXLIGHTMAPS (4) light styles bytes, and lightofs — offset into the lighting lump where this face's lightmap samples begin.
  • The visibility lump (LUMP_VISIBILITY, WinQuake/bspfile.h:68) is one big RLE-compressed bit matrix — see below.

CONTENTS_EMPTY/CONTENTS_SOLID/CONTENTS_WATER/CONTENTS_SLIME/CONTENTS_LAVA/CONTENTS_SKY, plus the internal-only CONTENTS_ORIGIN/CONTENTS_CLIP/CONTENTS_CURRENT_* (WinQuake/bspfile.h:137-151) are all small negative ints — negative so a single int field can double as either "this is a leaf with this content type" (when found as a node's children[] entry) or "this is a real node index" (when non-negative), with no separate tag needed. Leaf 0 is special-cased as the generic solid leaf, shared by every solid volume in the map and explicitly excluded from the vis leaf count (WinQuake/bspfile.h:211-212, and dmodel_t.visleafs, WinQuake/bspfile.h:87).

#Mod_LeafPVS / Mod_DecompressVis: RLE decompression

The PVS lump stores, per leaf, a bitset over all other leaves that are potentially visible from it — a full N×N matrix would be too large and too redundant (long runs of zero bits for far-away leaves), so it's run-length encoded: a non-zero byte is copied literally, a zero byte is followed by a repeat count.

decompressed is static — a single shared scratch buffer, which is fine because it is fully consumed (copied out or bit-tested) before the next call, and keeps the engine from allocating/freeing a MAX_MAP_LEAFS/8 = 1024-byte buffer every leaf-crossing. If leaf->compressed_vis is NULL (no vis data compiled, visofs == -1 in the leaf), the function fills the whole row with 0xff — "everything visible" — matching what a level with no vis pass (a -novis qbsp compile) should behave like. Mod_LeafPVS special-cases leaf 0 (the shared solid leaf, leaf == model->leafs) by returning mod_novis (WinQuake/model.c:36, all-0xff, initialized in Mod_Init at WinQuake/model.c:53-54) rather than trying to decompress a vis row for a leaf that was never assigned one — the camera should never actually be inside leaf 0, but this keeps the function total.

The RLE scheme buys enormous savings for typical Quake levels: PVS rows are naturally sparse (most leaves see only a small local neighborhood), and long zero runs from architecturally-separated rooms compress to two bytes each. This was a deliberate memory/CPU trade for the era — vis.exe's offline flood-fill visibility computation is expensive, but it lets the runtime skip drawing (or even touching) the vast majority of a level's geometry every frame on hardware with no depth buffer to rely on. See Michael Abrash's Black Book chapters on Quake's visibility system for the design history: https://www.jagregory.com/abrash-black-book/

#R_MarkLeaves, visframe, and r_novis

R_MarkLeaves walks the decompressed PVS bitset for the leaf the camera currently occupies and stamps a monotonically increasing r_visframecount (WinQuake/r_main.c:89) onto every node on the path from each visible leaf up to the root:

Two things worth noting. First, the early-out r_oldviewleaf == r_viewleaf means the entire PVS walk is skipped whenever the camera hasn't crossed into a new leaf since last frame — in a typical frame where the player is standing still or moving within one room, this function does nothing at all, which matters a great deal at 1996 frame budgets. Second, leafs[i+1] — vis bit i corresponds to leaf i+1, because leaf 0 (the shared solid leaf) is never included in the PVS matrix (dmodel_t.visleafs explicitly excludes it, WinQuake/bspfile.h:87). The do { ... node = node->parent; } loop stops early if it finds a node already marked for this r_visframecount — since an ancestor being already marked means everything further up is too, this turns what could be a full-tree-height walk per leaf into an amortized near-constant cost once the upper tree is marked.

r_novis (WinQuake/gl_rmain.c:86, registered WinQuake/gl_rmisc.c:189) is a debug/benchmarking cvar: when set, R_MarkLeaves fabricates an all-0xff "solid" vis buffer instead of decompressing the real PVS, forcing the entire level to be considered potentially visible every frame regardless of camera movement (note the !r_novis.value in the early-out, so toggling it forces re-marking even from a stationary viewpoint). This is invaluable for isolating PVS-culling costs/bugs from frustum-culling and rasterization costs, and for auditing whether a level's vis compile is actually saving meaningful geometry. The software renderer's R_MarkLeaves (WinQuake/r_main.c:491-519) has no r_novis check at all — that cvar and its GL-only surrounding logic (mirror handling) live only in the GL path.

Only nodes/leaves marked for the current r_visframecount are recursed into by the surface-walking code (R_DrawWorld/R_RecursiveWorldNode), so PVS culling composes with frustum culling and the dnode_t bounding boxes to minimize the amount of BSP tree actually traversed and rasterized each frame.

#How the server also uses PVS: SV_FatPVS

The server needs a conceptually different query than the renderer: not "what's visible from a single point right now" but "what's visible from anywhere a bobbing, moving player might be this frame," used to decide which edicts to include in each client's unreliable update. SV_AddToFatPVS/SV_FatPVS (WinQuake/sv_main.c:367-416) compute the union (bitwise OR) of the PVS of every leaf within a small box around the client's eye point, by recursively descending the render tree and only pruning a subtree once the split plane is farther than 8 units from the point:

#Contents types: collision hulls vs. render nodes

Quake keeps two entirely separate trees per .bsp: the render tree (dnode_t/mnode_t, walked by Mod_PointInLeaf, R_MarkLeaves, R_LightPoint, R_MarkLights) and up to MAX_MAP_HULLS (4, WinQuake/bspfile.h:24) collision hulls (dclipnode_t/hull_t, walked by SV_HullPointContents/SV_RecursiveHullCheck in world.c). This split is a memory/precision trade characteristic of the whole engine: the render tree needs surface lists and tight leaf bounding boxes for drawing and PVS, but none of that is useful for collision, so the clip hulls strip it down to the two fields collision actually needs, and reuse (rather than duplicate) the plane array (hull->planes = loadmodel->planes, both here and in Mod_LoadClipnodes at WinQuake/model.c:963/975).

#Lightmaps and light styles: r_light.c

Static lighting is precomputed offline by light.exe into per-face lightmap samples referenced by dface_t.lightofs and loaded into msurface_t.samples/styles by Mod_LoadFaces (WinQuake/model.c:799-807, shown above). Dynamic lights (rockets, explosions, the muzzle flash) work the opposite direction: instead of sampling a point, R_PushDlights (WinQuake/r_light.c:115-130, called once per V_RenderView, WinQuake/view.c:1018) walks the render tree from each active dlight_t outward via R_MarkLights (WinQuake/r_light.c:69-107), setting a dlightbits bitmask on every surface within the light's radius:

05 · RenderRendering: from screen update to pixels (software and GL paths)

Quake ships two complete renderers behind one interface: a CPU-only, palette-based software rasterizer tuned to 1996 x86 hardware, and an OpenGL renderer that offloads rasterization and texture blending to the GPU. Both share the same BSP world, the same client-side entity list, and the same view-setup code in view.c; they diverge at R_RenderView, and each takes a fundamentally different route to the same goal — visible-surface determination and shading without wasting cycles on pixels the player will never see.

#Software renderer: edge-based visible-surface determination

The software path's central design constraint is that there is no rasterizer hardware at all — every filled pixel costs CPU cycles for texture sampling, lighting, and the write itself. On a 60-100MHz Pentium-class part in 1996, filling pixels twice (overdraw) was directly, linearly wasted work. So the software renderer inverts the naive "walk polygons, scan-convert each one, z-test each pixel" approach and instead computes exactly which pixel spans are visible before any texturing happens, via a global edge list and an active-surface stack sorted by depth — the technique Michael Abrash devotes roughly a dozen chapters of the Graphics Programming Black Book to (chapters 57-70, "Quake's Visible-Surface Determination" and related).

Texturing a lightmapped BSP surface in software means resampling the base texture and blending up to four lightstyles into it — expensive enough that Quake caches the composited result per surface rather than recomputing it every time the surface is visible. #Lightmaps and multitexture

Lightmaps are precomputed low-resolution light grids baked at BSP-compile time and, at runtime, packed into shared BLOCK_WIDTH x BLOCK_HEIGHT GL texture atlases (lightmaps[], WinQuake/gl_rsurf.c:55; up to MAX_LIGHTMAPS textures starting at texture_extension_number, WinQuake/gl_rsurf.c:1613-1614). Without multitexturing, Quake would have to render every lightmapped surface twice — once for the base texture, once more with the lightmap texture blended over it (visible in the disabled #if 0 legacy path at WinQuake/gl_rsurf.c:316). GL_ARB_multitexture/GL_SGIS_multitexture let both texture units be sampled and combined in a single rasterization pass, which is exactly what R_DrawSequentialPoly (WinQuake/gl_rsurf.c:413) does when available:

The extension probing itself lives in CheckMultiTextureExtensions and is the piece added in this branch's history for portability beyond Windows: WinQuake/gl_vidlinuxglx.c:548-581 checks for either GL_SGIS_multitexture or GL_ARB_multitexture and resolves the right entry points (glMTexCoord2fSGIS/glSelectTextureSGIS vs. glMultiTexCoord2fARB/glActiveTextureARB) via dlsym:

06 · ClientInput, client movement, and networking

This section traces a single control input from the physical keyboard/mouse through to bytes on the wire, and traces the reply back through delta-decoded entity updates to the interpolated positions the renderer draws. NetQuake's whole client architecture is built around one constraint that later dropped away in QuakeWorld: assume a fast, low-latency link (a LAN, or a modem talking to a local single-player "server" via the loopback driver), and optimize for simplicity and bandwidth rather than for hiding internet-scale latency.

#Where it sits in the frame

_Host_Frame (WinQuake/host.c:633-693) drives the whole pipeline once per frame:

  1. Sys_SendKeyEvents() — WinQuake/host.c:650 — pumps the OS message queue, which synchronously calls back into Key_Event.
  2. IN_Commands() — WinQuake/host.c:653 — lets the mouse/joystick driver generate button events (Windows mouse buttons are polled here, not via window messages).
  3. Cbuf_Execute() — WinQuake/host.c:656 — executes any +forward-style commands the key events queued into the command buffer.
  4. NET_Poll() — WinQuake/host.c:659.
  5. CL_SendCmd() is called from one of two places depending on topology: WinQuake/host.c:663 (if (sv.active) CL_SendCmd();, before the server simulates — a listen server samples input before running the world), or WinQuake/host.c:686 (if (!sv.active) CL_SendCmd();, for a pure client, after the server-frame block but before waiting on the network — see the comment at WinQuake/host.c:684-685: "if running the server remotely, send intentions now after the incoming messages have been read").
  6. CL_ReadFromServer() — WinQuake/host.c:693 — only when cls.state == ca_connected; this both drains the socket and calls CL_ParseServerMessage, CL_RelinkEntities, CL_UpdateTEnts.

#Input: Sys_SendKeyEvents and Key_Event

On Windows, Sys_SendKeyEvents (WinQuake/sys_win.c:641-655) is just a PeekMessage/GetMessage/DispatchMessage pump; the actual key translation happens in the window procedure, which eventually calls Key_Event(int key, qboolean down) (WinQuake/keys.c:599). Key_Event is the single funnel for every physical input source — keyboard, mouse buttons (WinQuake/in_win.c:561, 567, 659, 665), joystick buttons (WinQuake/in_win.c:982, 988, 1015, 1020) all call it with a "key number" and up/down state.

The design problem Key_Event solves: keybindings map a keynum to a command string, and "button" commands (leading +) need matching press/release pairs even though two different physical keys can be bound to the same logical action (e.g. mouse2 and space both bound to +jump). The fix is to pass the keynum as a text argument to the queued command, so the release handler (KeyUp, see below) knows which physical key came up:

On key-down, the same routing happens in the other direction, again appending the keynum as a parameter for + commands:

Note this never touches usercmd_t directly — it only appends text to the console command buffer (Cbuf_AddText), which Cbuf_Execute() runs later in the same frame (WinQuake/host.c:656). This is the same mechanism used for ordinary console commands, which is why every movement key can also be bound to an arbitrary console command string.

{
	float		val;
	qboolean	impulsedown, impulseup, down;

	impulseup = key->state & 4;

CL_ParseUpdate(int bits) (WinQuake/cl_parse.c:330-483) implements the core bandwidth optimization of the whole protocol: rather than resending every field of every visible entity every frame, the server sends only a bitmask of which fields changed, and the client fills in anything absent from its own cached baseline. The bitmask itself can be extended past the initial byte via U_MOREBITS (WinQuake/protocol.h:25, plus U_ANGLE1 etc. defined up to U_LONGENTITY at WinQuake/protocol.h:35-41):

For each of position/angle per axis, the field is either read from the wire (bit set) or copied from the entity's baseline (the state sent once at level-load via svc_spawnbaseline/CL_ParseBaseline, WinQuake/cl_parse.c:491+) — most entities are stationary or move predictably, so most bits are usually clear (baseline itself is filled in by CL_ParseBaseline, WinQuake/cl_parse.c:491-..., dispatched from svc_spawnbaseline, WinQuake/cl_parse.c:868):

Note the shift-before-read: msg_origins[1] (the previous update) is set from the outgoing msg_origins[0] before msg_origins[0] is overwritten with the new value. msg_origins[0]/msg_angles[0] are "newest", [1] is "one update ago" — this two-slot history is exactly what CL_RelinkEntities interpolates between (next section). U_NOLERP lets the server force a hard snap (e.g. teleporters) instead of a smooth blend.

#Entity interpolation: entity_t, cl.mtime, CL_RelinkEntities

entity_t (WinQuake/render.h:39-70) is the client-side render entity; the fields relevant here are the two-deep history buffers:

origin/angles are what the renderer actually draws; msg_origins[2] / msg_angles[2] are raw server snapshots. The client never draws a raw snapshot directly — CL_RelinkEntities (WinQuake/cl_main.c:442-...) blends between the two most recent snapshots using a fraction computed by CL_LerpPoint (WinQuake/cl_main.c:391-408), based on where cl.time (the client's local clock, advanced every frame in CL_ReadFromServer) sits between the timestamps of the last two server messages, cl.mtime[0] and cl.mtime[1] (double mtime[2], WinQuake/client.h:196):

sv.active (running a local/listen server) forces frac = 1 — snap straight to the newest snapshot, no interpolation needed, because the local server ticks in lockstep with the client's own frame loop so there's no inter-packet gap to smooth over. For a remote connection, frac walks from 0 to 1 across the interval between the last two updates, and each entity is blended:

#Temp entities (cl_tent.c)

Transient, non-persistent effects — bullet impacts, explosions, lightning bolts, the grapple beam — don't get full entity_t slots in the delta-update system at all; they're one-shot events. CL_ParseTEnt (WinQuake/cl_tent.c:115-...) is invoked from svc_temp_entity (WinQuake/cl_parse.c:876), reads a TE_* type byte, and immediately spawns a particle effect, sound, or (for beams like TE_LIGHTNING1..3, WinQuake/cl_tent.c:216-227) a short-lived beam_t tracked outside the normal entity list. CL_UpdateTEnts (WinQuake/cl_tent.c:325-...), called every frame right after CL_RelinkEntities (WinQuake/cl_main.c:657), advances/expires those beams and dynamic lights each frame independent of any further server messages.

#Demo recording (cl_demo.c)

cl_demo.c lets CL_GetMessage transparently substitute file playback for NET_GetMessage: during cls.demoplayback, message bytes and view angles are read straight from cls.demofile instead of the socket (WinQuake/cl_demo.c:90-127), and the same CL_ParseServerMessage path handles them, since a demo is literally a recording of the raw server message stream. This is only possible because NetQuake has no client-side prediction — a demo is nothing but "replay these snapshots and interpolate," with no local simulation state to reconcile against a divergent recorded input stream.

#No client-side prediction: NetQuake vs. QuakeWorld

Everything above adds up to a specific architectural choice: NetQuake does not simulate the local player's movement client-side at all. CL_SendCmd builds a usercmd_t and ships it off; the client then does nothing but wait for the server's next svc_update/fast-update snapshot and interpolate between the last two received positions (CL_RelinkEntities, CL_LerpPoint above) — including for the local player's own entity (client_state_t, WinQuake/client.h:148-235, holds mtime[2] and the entity array uniformly for local and remote players). There is no CL_PredictMove in this codebase, no rewind-and-replay reconciliation, and no local physics integration of usercmd_t against the world. Movement feels immediate primarily because id assumed single-digit-millisecond round-trips (LAN, or the loopback driver for single-player), so the gap between "I pressed forward" and "the server's snapshot shows me having moved forward" is imperceptible.

That assumption breaks down over the public internet, which is exactly the problem QuakeWorld (QW/, a separate codebase in this repository — not covered here, and not modified for this doc) was built to solve. QuakeWorld introduces genuine client-side prediction: the client immediately, locally simulates its own usercmd_t against a local copy of player physics (QW/client/cl_pred.c), rendering the predicted result before the server's authoritative reply arrives, then reconciles/corrects when the server's snapshot (tagged with the input sequence it was computed from) comes back — snapping or smoothly correcting for misprediction. That is a fundamentally more complex model (it requires replaying buffered unacked commands against corrected server state) that NetQuake's single-player/LAN design goal never needed. The tradeoff is real: QuakeWorld's prediction can mask 100+ms of internet latency at the cost of occasional visible correction "pops"; NetQuake has zero prediction complexity but becomes visibly laggy the moment round-trip time grows, which is why it was effectively retired for competitive internet play once QuakeWorld shipped.

07 · SoundSound, plus misc engine plumbing

Quake's audio path mixes up to 128 simultaneous "channels" (looping ambients, dynamic entity sounds, and static level sounds) into a fixed-size paint buffer once per frame, entirely in integer math, then blits the result into the OS sound device's DMA buffer. The server never sends audio data — it sends a tiny svc_sound message naming a precached sound and an origin, and every connected client mixes it locally with its own stereo panning and distance attenuation. This section also tours the load-bearing plumbing that has nothing to do with any one subsystem but that every subsystem leans on: the status bar HUD, the console text buffer, the Cbuf/Cmd/Cvar command pipeline, the three custom memory allocators (Zone/Hunk/Cache), and the setjmp/longjmp error-recovery path that keeps a single bad frame from taking down the whole engine.

#Where it sits in the frame

_Host_Frame (WinQuake/host.c:633-727) is the top-level per-frame driver. Sound is mixed near the very end, after the screen has been redrawn:

S_Update is called with the render view's origin and axis vectors (r_origin, vpn, vright, vup) once the client is fully signed onto a game (cls.signon == SIGNONS); otherwise it's called with the null vectors so ambient/ancient channels still get serviced during loading screens. Command-buffer execution (Cbuf_Execute, WinQuake/host.c:657) and console/cvar handling happen earlier in the same frame, before networking and simulation — see the Call graph below for the full ordering.

#Sound: S_Update and spatialization

S_Update (WinQuake/snd_dma.c:721-808) is the once-per-frame entry point for the whole mixer. It updates the listener's position/orientation, refreshes the four ambient-sound channels, re-spatializes every active dynamic/static channel, and finally asks the mixer to paint audio into the DMA buffer:

Channels are a flat array channel_t channels[MAX_CHANNELS] (WinQuake/snd_dma.c:39, MAX_CHANNELS = 128, WinQuake/sound.h:130) partitioned into three regions by index range, documented right above the array in the header:

NUM_AMBIENTS is 4 (WinQuake/bspfile.h:209, water/sky/slime/lava loop sounds baked per-leaf into the BSP), and MAX_DYNAMIC_CHANNELS is 8 (WinQuake/sound.h:131) — one per entnum/entchannel slot picked by SND_PickChannel (WinQuake/snd_dma.c:354). Everything past that is a "static" channel: a fire-and-forget looping sound baked at map load (torches, etc.) that never moves. S_Update's loop at snd_dma.c:751-784 deliberately combines multiple static channels that share the same sfx into one channel's volume accumulation ("so we don't mix five torches every frame") — a cheap way to bound mixer cost on levels with dozens of identical ambient props, at the expense of losing individual stereo separation between them.

SND_Spatialize (WinQuake/snd_dma.c:398-444) computes per-channel left/right volume from 3D geometry:

Excerpt WinQuake/snd_dma.c:398-444
CWinQuake/snd_dma.c:398-444
void SND_Spatialize(channel_t *ch)
{
    vec_t dot;
    vec_t ldist, rdist, dist;
    vec_t lscale, rscale, scale;
    vec3_t source_vec;
	sfx_t *snd;

// anything coming from the view entity will allways be full volume
	if (ch->entnum == cl.viewentity)
	{
		ch->leftvol = ch->master_vol;
		ch->rightvol = ch->master_vol;
		return;
	}

// calculate stereo seperation and distance attenuation

	snd = ch->sfx;
	VectorSubtract(ch->origin, listener_origin, source_vec);
	
	dist = VectorNormalize(source_vec) * ch->dist_mult;
	
	dot = DotProduct(listener_right, source_vec);

	if (shm->channels == 1)
	{
		rscale = 1.0;
		lscale = 1.0;
	}
	else
	{
		rscale = 1.0 + dot;
		lscale = 1.0 - dot;
	}

// add in distance effect
	scale = (1.0 - dist) * rscale;
	ch->rightvol = (int) (ch->master_vol * scale);
	if (ch->rightvol < 0)
		ch->rightvol = 0;

	scale = (1.0 - dist) * lscale;
	ch->leftvol = (int) (ch->master_vol * scale);
	if (ch->leftvol < 0)
		ch->leftvol = 0;
}

This is the whole panning model: a dot product of the vector-to-source against the listener's right axis gives a [-1,1] pan bias, and linear distance falloff (scaled by dist_mult, which folds in the server's attenuation value) gives volume rolloff. There is no HRTF, no real-time convolution, no hardware 3D-audio dependency (Aureal A3D and EAX existed in 1996-97 but were far from universal) — id needed something that ran identically and cheaply on every sound card, down to ones with only a raw PCM DMA buffer and no mixing hardware. A dot-product pan plus linear attenuation is a handful of FPU ops per channel per frame, which is what made spatializing dozens of channels viable on a Pentium-class CPU with no dedicated DSP.

Note the special case at the top: sounds attached to the local view entity (cl.viewentity, e.g. weapon fire, pain grunts) always play at full, unpanned volume — imagine your own gunshot getting quietly panned to one ear because of a floating-point epsilon in your own origin vs. listener origin.

#Channels and the paint buffer mixer (snd_mix.c)

Once every channel's leftvol/rightvol are current, S_Update_ (WinQuake/snd_dma.c:856-902) figures out how far ahead of the current DMA play position to mix (_snd_mixahead, clamped to the DMA buffer size), restores/resumes the Windows DirectSound buffer if needed, and calls the actual mixer, S_PaintChannels (WinQuake/snd_mix.c:261-332):

paintbuffer is a fixed global array of portable_samplepair_t (int left/right accumulators, WinQuake/snd_mix.c:31), sized PAINTBUFFER_SIZE samples — never the full DMA buffer, which is why the outer while loop chunks the work. SND_PaintChannelFrom8/SND_PaintChannelFrom16 (WinQuake/snd_mix.c:346-393 and following) additively accumulate each channel's samples into paintbuffer[i].left/right using a precomputed scale table (SND_InitScaletable, WinQuake/snd_mix.c:334-341) for the 8-bit path — 32 volume buckets × 256 signed sample values, so an 8-bit sample times a volume level is a table lookup, not a multiply, at a time when integer multiplies were still relatively expensive relative to loads. Mixing is done in a wider-than-8/16-bit accumulator precisely so 32+ overlapping sounds can sum without per-sample clamping until the very end (S_TransferPaintBuffer, WinQuake/snd_mix.c:139, which does the final clamp/format conversion when writing into the DMA buffer). This "accumulate wide, clamp once at the edge" design is the standard trick for software mixing without a hardware mixer: it avoids the artifacts (and cost) of clamping after every single channel addition.

Sounds loop by adjusting ch->pos/ch->end against the cached sample data's loopstart (WinQuake/snd_mix.c:310-323) — when a channel's play cursor reaches ch->end and the underlying sfxcache_t has no loop point, the channel is simply cleared (ch->sfx = NULL) and drops out of the mix on the next S_Update.

#How sound events reach the client: svc_sound

The server never streams PCM — it only ever tells clients what to play. SV_StartSound (WinQuake/sv_main.c:118-171) packs an svc_sound message into either a client's reliable stream or, for map-relative broadcast, sv.datagram:

The entity number and the 0-7 channel slot are packed into a single short ((ent<<3) | channel, mirrored by the unpack ent = channel >> 3; channel &= 7; on the client), and volume/attenuation are only written at all if they differ from the server's compiled-in defaults (field_mask), keeping the common case down to a handful of bytes. sound_num is an index into the level's precached sound list (sv.sound_precache, looked up by linear scan at sv_main.c:139-142) rather than a filename, so the wire format never carries a string. Note the guard if (sv.datagram.cursize > MAX_DATAGRAM-16) return; (sv_main.c:135-136) — under packet pressure the server silently drops sound events rather than growing the datagram or blocking; a missed footstep sound is an acceptable loss, a dropped player-state update is not.

On the client, CL_ParseServerMessage's dispatch table hits case svc_sound: CL_ParseStartSoundPacket(); (WinQuake/cl_parse.c:830-832), and CL_ParseStartSoundPacket (WinQuake/cl_parse.c:101-136) does the mirror-image unpack and calls straight into S_StartSound:

S_StartSound (WinQuake/snd_dma.c:451 onward) then calls SND_PickChannel to claim a channel slot for that (entnum, entchannel) pair — channel 0 auto-allocates a free dynamic channel, channels 1-7 override anything already playing on that same entity/channel pair (see the doc comment at sv_main.c:107-111: "Each entity can have eight independant sound sources, like voice, weapon, feet, etc. Channel 0 is an auto-allocate channel, the others override anything allready running on that entity/channel pair") — then calls SND_Spatialize once immediately so the sound has correct volumes from its very first mixed frame (snd_dma.c:482).

#Brief: Sbar_Draw (status bar)

Sbar_Draw (WinQuake/sbar.c:926-1044) is called from SCR_UpdateScreen in both renderers (WinQuake/screen.c:901/909/931, WinQuake/gl_screen.c:885/893/914) once per drawn frame. It's a straightforward immediate-mode HUD painter: health, armor, ammo, weapon icons, and the frags/scoreboard overlay, blitted via Sbar_DrawPic/Sbar_DrawNum (sbar.c:260, sbar.c:350) from cached qpic_ts. Two details worth noting: it bails out early if the console is fullscreen (if (scr_con_current == vid.height) return;, sbar.c:928) or if it's already been redrawn for every visible page this frame (sb_updates >= vid.numpages, sbar.c:931) — sb_updates/Sbar_Changed() form a simple dirty-flag scheme so the status bar isn't recomposited when nothing in it changed, which mattered on page-flipped/paletted software rendering where blitting the sbar region was not free.

#Brief: the console

The console keeps its scrollback in a single flat ring-style char buffer, con_text, sized CON_TEXTSIZE = 16384 bytes (WinQuake/console.c:35), allocated once off the hunk at startup: con_text = Hunk_AllocName (CON_TEXTSIZE, "context"); (WinQuake/console.c:229). Con_Printf (WinQuake/console.c:377) is the sink every subsystem funnels diagnostic and gameplay text through (Con_Printf: %s not precacheed, Unknown command, etc., seen throughout this doc), and Con_DrawConsole (WinQuake/console.c:580) paints the visible slice of that buffer plus the input line when the console is pulled down. Resizing the video mode reflows the buffer's line width and re-wraps existing text in place (Con_CheckResize, WinQuake/console.c:153-204) rather than dropping scrollback — a small but deliberate UX choice given how often players resized/changed video modes mid-session on 90s hardware.

#Brief: Cbuf/Cmd/Cvar plumbing

Every typed command, config-file exec, alias expansion, and +/- command-line argument funnels through one text pipeline. Cbuf_AddText (WinQuake/cmd.c:86-99) appends raw text to a single global sizebuf_t cmd_text (8192 bytes, allocated in Cbuf_Init, cmd.c:73-76); Cbuf_InsertText (cmd.c:111-136) instead splices text at the front of the buffer (used by exec/alias expansion so a config file's commands run before whatever was already queued after it). Once per frame, Cbuf_Execute (WinQuake/host.c:657, calling WinQuake/cmd.c:143-193) pulls lines out up to the next \n or unquoted ;, and hands each to Cmd_ExecuteString:

The lookup order is fixed and significant: registered engine commands (a linked list, cmd_functions) win first, then user aliases, and only then cvars — so a command can never be shadowed by a same-named cvar, but a cvar can be shadowed by a command (Cvar_RegisterVariable refuses to register a cvar whose name collides with an existing command, WinQuake/cvar.c:163-167). Cvar_Command (WinQuake/cvar.c:187-205) is what makes typing a bare cvar name print its value and typing name value set it — it's just one more fallback tried by Cmd_ExecuteString, not a separate parser. Cvar_Set (cvar.c:104-128) always re-Z_Mallocs the string storage (freeing the old one), so cvar values live on the Zone heap, not the hunk — they're small, and they can be freed/reallocated at arbitrary times, which the hunk's stack-discipline allocator cannot do (see below).

#Brief: Hunk/Zone/Cache allocators (zone.c)

Quake predates malloc/free being a workable strategy for a real-time engine on 1996-era machines: general-purpose heaps of that era fragment badly under long alloc/free churn, offer no visibility into where memory went, and have no notion of "throw this away if we need the room" — all things a game that loads/unloads whole levels every few minutes needs. zone.c implements three allocators layered over each other, each suited to a different lifetime pattern:

  • Zone (Z_Malloc, WinQuake/zone.c:142) is a classic best-fit free-list allocator over a fixed-size arena (DYNAMIC_SIZE = 0xc000, zone.c:24) with block headers carrying a size/tag/id and a trash-detection sentinel (ZONEID, zone.c:26) checked by Z_CheckHeap (zone.c:247-262). It's for small, short-lived, arbitrarily-freed allocations — strings, cvar values — the doc comment says as much: "The zone calls are pretty much only used for small strings and structures, all big things are allocated on the hunk" (zone.c:59-60).
  • Hunk (Hunk_AllocName, WinQuake/zone.c:399-427) is a two-ended bump/stack allocator over one huge arena (hunk_base/hunk_size) — permanent, load-time data (server/client game state, the current level's BSP) grows up from hunk_low_used, and short-lived per-frame/per-scope temp allocations grow down from the top via hunk_high_used (Hunk_HighMark/Hunk_FreeToHighMark, zone.c:452-474). There is no per-block free; you only ever roll the mark back to a previous low/high watermark, which is why it's essentially free (a pointer subtraction) and immune to fragmentation — the tradeoff is that anything on the hunk must be freed in strict LIFO order relative to what was allocated after it.
  • Cache (Cache_Alloc, WinQuake/zone.c:871-903) sits inside the hunk's free middle region (between the low and high marks) and is the one allocator in the trio that's allowed to evict its own contents on demand. This is the piece that makes a fixed-size hunk workable at all on a machine with a few dozen megabytes of RAM: it lets the engine hold onto expensive-to-regenerate resources (decompressed alias models, decoded sound effects) as long as there's room, and reclaim them transparently the moment the hunk needs to grow.

Cache_Alloc walks a doubly linked list of cache_system_t blocks threaded through the hunk's middle, and also keeps a second, orthogonal doubly linked list — lru_prev/lru_next — purely for recency:

When Cache_TryAlloc (zone.c:680-750) can't find a big-enough free gap between existing cache blocks (searched bottom-up, zone.c:702-731), Cache_Alloc frees the block at cache_head.lru_prev — the least-recently-touched entry — and retries; a textbook LRU eviction loop. Every successful lookup moves its block to the front of the LRU list: Cache_Check (zone.c:849-863) runs both after a fresh alloc and on every cache hit, unconditionally re-linking via Cache_UnlinkLRU/Cache_MakeLRU (zone.c:858-860) — merely reading a cached asset protects it from the next eviction pass. When the hunk's low or high mark needs to grow past where cached data sits, Cache_FreeLow (zone.c:606-619) / Cache_FreeHigh (zone.c:628-648) relocate the block out of the way (Cache_Move, zone.c:575-597) or, if there's nowhere to move it, evict it outright — eviction is forced by hunk growth pressure, not just by running out of cache space.

This is exactly the pattern used for alias-model data: Mod_LoadAliasModel builds the model into scratch hunk space, then copies the finished, relocatable blob into the cache (Cache_Alloc (&mod->cache, total, loadname);, WinQuake/model.c:1654, mirrored in WinQuake/gl_model.c:1640) and frees the scratch hunk space back (Hunk_FreeToLowMark, model.c:1659). Every later access goes through Mod_Extradata (WinQuake/model.c:64-77), which calls Cache_Check first and, only on a miss (the model got evicted under memory pressure), reloads it from disk via Mod_LoadModel:

Precached sound effects go through the identical pattern via snd_mem.c (Cache_Alloc ( &s->cache, len + sizeof(sfxcache_t), s->name);, WinQuake/snd_mem.c:139, checked on every play attempt via Cache_Check (&sfx->cache) at WinQuake/snd_dma.c:970).

Worth being precise that the software renderer's texture surface cache — the lightmapped, mip-scaled wall/floor textures rasterized by R_DrawSurface in WinQuake/r_surf.c:248-331 and fetched via D_CacheSurface — is not built on zone.c's Cache_Alloc. It's a separate, purpose-built allocator in WinQuake/d_surf.c: a fixed-size ring buffer (sc_base/sc_size/sc_rover, d_surf.c:29-30) of surfcache_t blocks (WinQuake/d_local.h:37-49) sized at startup by D_SurfaceCacheForRes (d_surf.c:35-53, larger at higher resolutions since more distinct texture/lightmap combinations are visible per frame). D_SCAlloc (d_surf.c:130-209) evicts by walking forward from a rover pointer and coalescing/overwriting whatever it finds in its way — a FIFO/wrap eviction, not a true LRU — nulling each victim's owner pointer (*sc_rover->owner = NULL) so the next lookup treats it as a cache miss and regenerates the blit. The two systems are architectural siblings — both trade a fixed memory budget for on-demand regeneration — but separate implementations: zone.c's Cache holds whole assets (models, sounds) inside the shared hunk, while d_surf.c's surface cache is a renderer-private heap tuned for the volume and churn of on-screen texture surfaces every frame.

#Brief: Host_Error and the setjmp/longjmp recovery path

C has no exceptions, and Quake needs a way to unwind an arbitrary number of call frames — out of the middle of BSP traversal, physics, or a QuakeC opcode handler — back to the top of the frame loop when something recoverable-but-serious goes wrong (a corrupt server message, a QuakeC runtime fault, a missing model). The mechanism is setjmp/longjmp with one global jump buffer:

_Host_Frame establishes the recovery point at the very top of every single frame:

Host_Error (WinQuake/host.c:121-149) is the landing pad every subsystem calls when it hits a non-fatal-to-the-process-but-fatal-to-this-game error. It re-entrancy-guards itself (static qboolean inerror, escalating to a hard Sys_Error if Host_Error is somehow called while already unwinding, host.c:127-128), shuts the local server down if one is running (Host_ShutdownServer, host.c:138-139), disconnects the client (CL_Disconnect, host.c:144), and then calls longjmp (host_abortserver, 1) (host.c:149) — controlled unwind straight back to the setjmp at the top of _Host_Frame, skipping the rest of whatever frame-processing code was on the stack, no matter how deep. Dedicated servers deliberately opt out of recovery (if (cls.state == ca_dedicated) Sys_Error (...), host.c:141-142) — a dedicated server has no player-facing "you got disconnected, back to the menu" experience to fall back to, so a Host_Error there is treated as fatal and the process exits, on the theory that a corrupted dedicated server should restart rather than limp along in an unknown state.

The alternative — plumbing an error return code through every function on the call path from QuakeC opcode dispatch up through Host_Frame — would have meant touching essentially the entire codebase and manually unwinding partially-initialized state at every level. setjmp/longjmp gets the same "abandon this frame, get back to a known-good top-level loop" behavior in two lines, at the cost of not running any C++-style destructors/cleanup along the way — acceptable here because the state being abandoned (partially loaded level, partially processed network packet) is precisely the state Host_ShutdownServer/CL_Disconnect are about to reset wholesale anyway.
